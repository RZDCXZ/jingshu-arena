# 竞枢基础 RC 规格

Status: ready-for-agent

## Problem Statement

作品集需要一个能够真实证明复杂全栈交付能力的电竞场馆经营产品，而不是只有静态页面、通用后台模板或彼此断开的功能样例。访客必须能够在无需注册、无需真实支付、无需开发者陪同的情况下，连续体验顾客预约、到店使用、商品订单、设备报修、库存领用、门店管理和总部比较，并看到同一业务状态如何跨角色变化。

该产品同时必须诚实处理演示边界：不服务真实门店、不收集真实身份、不接入真实支付或设备，不把本地小程序伪装成与 Web 后台实时同步；又必须真正实现预约冲突、库存事务、权限隔离、状态机、审计、统计、部署和验证。最终交付需要达到可公开访问、可复现、可测试、可解释和可发布的基础 RC 水平。

## Solution

构建“竞枢 · Jingshu Arena”基础 RC：一个服务单一虚构经营方、固定三家门店的多端经营协同演示。Web 端为每位访客创建独立且可重置的沙箱，顾客、店员、店长和总部运营四个公开角色在同一沙箱内顺序协作；原生微信小程序复用同一套纯 TypeScript 领域规则和合成故事，但通过本地存储独立运行。

系统以完整的业务模型、数据库约束和事务实现预约、商品订单、统一库存账本、报修、座位维护、会员、体验券、排班、考勤、交接、看板、导出和审计。主演示从旗舰店立即预约开始，经由到店、商品订单和耳机故障，最终完成分段模拟退款、备件领用、维修验证和跨店看板更新。公开体验持续标明演示数据与模拟支付边界，并以隔离、限流、私有图片净化、双时钟、确定性种子、自动化门禁和发布证据保证安全与可信度。

## User Stories

1. 作为首次访客，我希望在创建任何沙箱前了解产品用途、演示边界和四个角色，从而判断应该从哪个入口开始体验。
2. 作为首次访客，我希望无需注册、密码或真实身份即可进入演示，从而快速验证产品能力。
3. 作为访客，我希望拥有与其他访客隔离的完整沙箱，从而可以自由操作而不破坏别人的演示。
4. 作为访客，我希望复制公开地址给别人时对方获得自己的沙箱，从而不会泄露或共享我的可写状态。
5. 作为访客，我希望所有页面持续标明“演示数据”，从而不会把虚构经营信息误认为真实服务。
6. 作为访客，我希望每个模拟支付步骤都明确说明不会扣款，从而不会误解为真实交易。
7. 作为访客，我希望通过可收起的主演示清单了解下一步，从而无需开发者陪同也能走完整个故事。
8. 作为访客，我希望主演示清单从真实业务事件推导进度，从而不会把点击过按钮误认为业务已经成功。
9. 作为访客，我希望在同一沙箱内切换四个角色，从而观察同一业务对象在不同职责下的变化。
10. 作为访客，我希望切换角色前得到未提交表单提示，从而避免无意丢失输入。
11. 作为多标签页访客，我希望旧标签在角色变化后停止旧角色写操作，从而避免使用失效权限提交命令。
12. 作为访客，我希望能够把沙箱业务时钟推进到下一事件或向前半小时，从而无需真实等待数小时即可演示超时和自动状态变化。
13. 作为访客，我希望演示时间只能向前且有明确上限，从而保持业务事件因果顺序可信。
14. 作为访客，我希望重置前看到会清除四个角色数据的确认，从而不会误删当前演示故事。
15. 作为访客，我希望重置后得到全新的标准种子沙箱和归零的演示清单，从而可以稳定复现主演示。
16. 作为访客，我希望系统容量不足或后端故障时仍能浏览只读标准快照，从而至少能够了解产品而不会看到伪造的保存成功。
17. 作为移动端访客，我希望顾客 H5 从 360px 宽度起完整可用，从而能在常见手机和微信内置浏览器中体验。
18. 作为键盘或辅助技术使用者，我希望获得语义结构、可见焦点、错误关联和非颜色唯一提示，从而能够完成核心路径。
19. 作为顾客，我希望浏览三家虚构门店的详情和营业时间，从而选择适合的门店。
20. 作为顾客，我希望按日期、时段、区域和机型查看座位图，从而找到符合需求的座位。
21. 作为顾客，我希望座位可订性针对所选时段计算，从而不会因未来预约而误判当前座位状态。
22. 作为顾客，我希望看到每个半小时价格片段和总价，从而理解跨价格时段预约如何计费。
23. 作为顾客，我希望在旗舰店发起两小时立即预约，从而可以立刻进入主演示闭环。
24. 作为顾客，我希望预约未来七天内的一至八小时连续时段，从而体验正常预约能力。
25. 作为顾客，我希望系统阻止自己跨门店创建时间重叠的有效预约，从而避免无法履行的重复安排。
26. 作为顾客，我希望冲突时得到明确的座位或个人时段冲突提示，从而可以重新选择。
27. 作为顾客，我希望待确认预约为我保留座位十分钟，从而有时间完成模拟支付。
28. 作为顾客，我希望创建预约时排他占用所选体验券，从而不会把同一张券用于两笔交易。
29. 作为顾客，我希望模拟支付成功后金额与创建时价格快照一致，从而不会被后台后续改价影响。
30. 作为顾客，我希望在预约开始前取消待确认或已确认预约，从而释放不再需要的座位时段。
31. 作为顾客，我希望查看到店倒计时和允许办理到店的时间窗口，从而知道何时可以到店。
32. 作为顾客，我希望预约爽约、取消、完成和设备中断都留下清楚历史，从而理解最终结果。
33. 作为顾客，我希望设备故障中断时看到已计费片段和未来退款片段，从而理解模拟退款计算。
34. 作为顾客，我希望查看连锁级会员档案、青铜/白银/黄金等级和成长值，从而理解跨店成长体系。
35. 作为顾客，我希望完成有效预约或商品订单后按最终模拟金额获得成长值，从而看到消费与会员成长联动。
36. 作为顾客，我希望查看体验券的适用门店、品类、时段、最低金额和有效期，从而选择可用权益。
37. 作为顾客，我希望每笔交易最多使用一张固定金额体验券，从而获得可解释的优惠结果。
38. 作为已到店或使用中的顾客，我希望为同店预约创建柜台取货商品订单，从而在体验期间购买商品。
39. 作为顾客，我希望浏览门店实际上架的商品和售价，从而不会看到不可销售备件或其他门店配置。
40. 作为顾客，我希望整单库存不足时订单完全失败，从而不会得到缺行或部分成功的订单。
41. 作为顾客，我希望待模拟支付订单保留库存十分钟，从而有时间确认而不被其他订单抢走。
42. 作为顾客，我希望查看商品名称、单价、数量、优惠和总额快照，从而让历史订单不受后续改名改价影响。
43. 作为顾客，我希望查看订单从已模拟支付、制作中、待取到已完成的进度，从而知道何时到柜台领取。
44. 作为顾客，我希望在制作开始前取消订单并释放库存与体验券，从而撤销尚未履行的交易。
45. 作为顾客，我希望预约因设备故障结束后，已模拟支付订单仍可继续柜台履约，从而不会丢失已经确认的商品。
46. 作为顾客，我希望直接为当前座位提交报修单，从而快速报告设备故障。
47. 作为顾客，我希望重复报修同一座位时看到现有未关闭报修单，从而避免创建重复工单。
48. 作为顾客，我希望可选上传最多三张经过净化的故障图片，从而补充问题证据而不泄露图片元数据。
49. 作为顾客，我希望拒绝图片权限或上传失败时仍能用文字或样例图报修，从而不被设备能力阻塞。
50. 作为顾客，我希望只看到公开处理动态和验证结果，从而了解进度而不会看到门店内部笔记。
51. 作为顾客，我希望统一查看自己的预约、订单、报修和模拟退款历史，从而回顾完整体验。
52. 作为顾客，我希望系统不要求真实姓名、电话、邮箱、地址或证件，从而无需提交个人敏感信息。
53. 作为店员，我希望查看所属门店今日预约、到店、使用中和异常队列，从而安排现场处理。
54. 作为店员，我希望在预约开始前三十分钟至开始后十五分钟办理到店，从而遵守统一到店规则。
55. 作为店员，我希望只能在计划开始后把已到店预约推进为使用中，从而避免提前开台。
56. 作为店员，我希望提前结束使用中预约并记录原因，从而处理顾客主动结束或设备故障。
57. 作为店员，我希望在预约进入使用中前带原因取消，从而处理现场异常且保留审计证据。
58. 作为店员，我希望查看已模拟支付商品订单并依次推进制作中、待取和已完成，从而完成柜台履约。
59. 作为店员，我希望在订单完成前带原因取消，从而正确区分制作前释放库存与制作后损耗。
60. 作为店员，我希望查看本店账面、预留和可用库存，从而判断订单和维修是否有物料。
61. 作为店员，我希望只能通过订单或报修改变库存，从而不能绕过业务对象直接改余额。
62. 作为店员，我希望主动为座位创建报修单，从而记录现场发现而非顾客提交的故障。
63. 作为店员，我希望为新建报修分派处理人和优先级，从而建立明确责任与处理顺序。
64. 作为处理人，我希望开始维修时原子地把座位置为维护中，从而使预约与维修状态保持一致。
65. 作为处理人，我希望进入维修时自动处理当前和未来受影响预约，从而不会继续出售故障座位。
66. 作为处理人，我希望在处理中领用备件并产生关联库存流水，从而保证维修消耗可追溯。
67. 作为处理人，我希望关闭前退回未使用备件，从而恢复实际可用库存。
68. 作为处理人，我希望提交解决说明后进入待验证，从而让另一名同店员工确认结果。
69. 作为验证人，我希望验证失败时把报修退回处理中并保留原因，从而继续维修且保持座位维护。
70. 作为验证人，我希望验证成功时原子关闭报修并恢复座位，从而避免座位状态与工单结果矛盾。
71. 作为店员，我希望查看自己的班次并执行模拟签到和手动签退，从而演示基本考勤流程。
72. 作为店员，我希望迟到或缺勤由班次和沙箱业务时钟推导，从而不依赖伪造的定位或门禁。
73. 作为交班员工，我希望提交未完成预约、订单、报修和库存告警快照，从而把当前门店事项交给下一班。
74. 作为交班员工，我希望提交后即可签退且交接不可编辑，从而保留真实交班时点的证据。
75. 作为接班员工，我希望随后确认交接，从而记录接班责任已经承接。
76. 作为店员，我希望无法读取或操作其他门店受限数据，从而维持门店职责边界。
77. 作为店长，我希望维护所属门店展示资料、营业时间、区域和座位，从而配置门店经营资源。
78. 作为店长，我希望为座位分配总部机型档案并保证店内座位编号唯一，从而保持座位图一致。
79. 作为店长，我希望创建未来生效且不重叠的价格计划版本，从而改价而不重写历史预约。
80. 作为店长，我希望只能归档已经被业务引用的配置，从而保留历史可追溯性。
81. 作为店长，我希望配置本店商品上架状态、售价和库存阈值，从而独立管理门店销售。
82. 作为店长，我希望执行手工入库并生成正向库存流水，从而记录补货事实。
83. 作为店长，我希望通过盘点输入实际数量并生成差额流水，从而校准库存而不覆盖历史。
84. 作为店长，我希望用补偿流水修正错误库存操作，从而保留原记录和纠错原因。
85. 作为店长，我希望查看并处理低库存告警，从而及时识别商品或备件不足。
86. 作为店长，我希望创建、编辑和停用本店背景员工，同时保护公开演示人物，从而维护人员数据而不破坏角色入口。
87. 作为店长，我希望安排四至十二小时且不重叠的半小时对齐班次，从而生成可执行排班。
88. 作为店长，我希望人员覆盖不足时得到告警但仍能保存排班，从而发现风险而不被僵硬规则阻塞。
89. 作为店长，我希望通过追加考勤更正修正迟到、缺勤或签退，从而保留原始考勤事实。
90. 作为店长，我希望查看本店订单、库存、排班、报修和经营看板，从而掌握单店运营状态。
91. 作为店长，我希望查看并导出本店关键操作审计，从而追踪谁在何时改变了什么。
92. 作为店长，我希望无法读取或修改其他门店受限数据，从而不越过单店管理范围。
93. 作为总部运营，我希望维护连锁级商品资料和机型档案，从而让三店共享一致基础配置。
94. 作为总部运营，我希望查看和配置固定三家门店的展示、区域、座位、价格与商品范围，从而管理连锁标准。
95. 作为总部运营，我希望并列比较三店模拟营业额、运营座位利用率和维护不可用率，从而区分需求表现与设备损失。
96. 作为总部运营，我希望比较订单完成率、库存告警、报修、考勤和交接异常，从而发现门店差异。
97. 作为总部运营，我希望查看三店人员与排班汇总，从而了解组织覆盖而不直接替门店排班。
98. 作为总部运营，我希望查看和导出当前沙箱全部三店审计，从而核验跨店配置和经营变化。
99. 作为总部运营，我希望导出当前筛选的预约、订单、库存流水、报修、排班和审计 CSV，从而进一步分析数据。
100. 作为总部运营，我希望无法执行到店、制作、维修、签到或交接等一线动作，从而避免总部变成绕过规则的超级管理员。
101. 作为小程序体验者，我希望在原生微信界面中完成顾客侧门店、预约、会员、订单、报修和历史流程，从而验证原生小程序实现能力。
102. 作为小程序体验者，我希望业务数据保存在本地并明确不与 Web 沙箱同步，从而理解真实实现与 Mock 边界。
103. 作为小程序体验者，我希望关闭并重新打开后本地状态仍然存在，从而验证持久化而非一次性页面状态。
104. 作为小程序体验者，我希望版本升级执行本地 schema 迁移，从而保留可兼容的数据演进路径。
105. 作为小程序体验者，我希望主动重置到当前版本标准种子，从而可以重复体验顾客流程。
106. 作为系统维护者，我希望所有 Web 可变记录按沙箱隔离且门店记录带门店范围，从而阻止跨沙箱和跨店数据泄露。
107. 作为系统维护者，我希望 Postgres 最终阻止座位和顾客时段重叠，从而在并发请求下仍不会双重预约。
108. 作为系统维护者，我希望库存预留、扣减、流水和业务状态在同一事务提交，从而不会出现负库存或半成记录。
109. 作为系统维护者，我希望关键命令支持幂等重试，从而让弱网和超时不会创建重复业务对象。
110. 作为系统维护者，我希望状态变化同时保存当前状态、业务事件和审计事件，从而兼顾高效查询与完整解释。
111. 作为系统维护者，我希望业务期限使用沙箱业务时钟而安全与清理期限使用真实服务器时间，从而避免演示快进绕过安全规则。
112. 作为系统维护者，我希望沙箱通过确定性生成器在单一事务中完整物化，从而让列表、统计和导出从首次进入就一致。
113. 作为系统维护者，我希望新部署兼容仍在有效期内的旧种子版本，从而不打断正在进行的演示。
114. 作为系统维护者，我希望过期沙箱先停止访问再分批清理 Blob 和业务行，从而让删除失败可重试且不长期锁表。
115. 作为系统维护者，我希望 SSE 只发送失效通知并在不可用时退化为轮询，从而保持数据库和 API 为唯一权威。
116. 作为系统维护者，我希望图片先进入私有隔离区并经服务端净化，从而不保存匿名访客上传的定位元数据或主动内容。
117. 作为系统维护者，我希望结构化日志、审计和错误响应采用字段白名单，从而不泄露令牌、Secret、图片或内部实现。
118. 作为系统维护者，我希望数据库迁移采用前向 expand/contract，从而可以回滚应用而不依赖破坏性 down migration。
119. 作为作品集审阅者，我希望看到真实运行的多角色闭环、状态机、权限和事务证据，从而判断项目不是静态模板。
120. 作为作品集审阅者，我希望获得中英双语说明、架构与领域文档、测试报告、截图索引和演示视频，从而快速理解实现质量。
121. 作为作品集审阅者，我希望看到大陆三网、主流浏览器、微信内置浏览器和真机验证记录，从而判断公开演示的可访问性。
122. 作为代码审阅者，我希望未完成工作公开在功能分支而主分支保持可发布，从而既能观察开发过程又不会把半成品自动部署生产。

## Implementation Decisions

### 交付与执行

- 目标是完成阶段 A 至 E 的完整基础 RC，而非只交付规划文档或本地版本。
- 基础设施探针延后到部署阶段；探针未通过前不得判定正式 RC 完成，受 ADR-0001 约束。
- 视觉方向在制作设计稿时再决定。
- GitHub 远端从开发开始即保持公开，未完成代码和文档不隐藏；所有未完成能力、已知限制与未通过门禁必须如实标注，仓库不得包含 Secret、真实个人数据或不可再分发资产。
- 全部开发工作在公开的 `codex/jingshu-basic-rc` 分支完成，未完成但通过相应阶段检查的提交可以持续推送；不直接在 `main` 上开发。
- `main` 始终保持可发布状态；功能分支只有在全部 RC 合并门禁通过后才能合并，合并成功后允许自动部署生产。
- 正式 RC 使用 MIT License；第三方依赖与素材继续接受许可证和归属检查。
- 仓库提供相互链接的中文主说明与完整英文说明，两者保持架构、运行方式、边界、测试、演示入口和已知限制一致。

### 产品边界

- 基础 RC 服务一个虚构连锁经营方，固定包含三家门店，不实现多经营方或多租户能力。
- 每位 Web 访客拥有独立沙箱；四个演示角色共享该沙箱的业务状态。
- 小程序使用独立本地沙箱，与 Web 沙箱使用相同业务叙事但不实时同步。
- Web 首次访问只展示产品用途、演示数据说明、真实与 Mock 边界以及四个角色入口；访客选择角色后才创建沙箱，爬虫或只读浏览首页不产生业务数据。
- 沙箱由安全会话绑定，不把 `sandbox_id` 或可读写凭证放入 URL；其他人打开复制的公开地址会创建自己的独立沙箱。
- 全部 Web 角色页面持续显示“演示数据”标识；模拟支付入口、确认和结果始终明确写明“不扣款”，不能只在首次进入时提示。
- 产品不提供真实姓名、电话、邮箱、地址或证件输入字段，只使用固定虚构人物；所有自由文本入口提示访客不要填写真实个人信息。

### 演示授权、重置与审计

- 顾客、店员、店长和总部运营四个预设角色都可以由公开访客选择，不实现真实注册、密码或员工邀请。
- 角色切换由服务端签发 HttpOnly、Secure、同站会话；服务端从会话读取沙箱、演示人物、角色和门店范围。
- 当前角色属于整个浏览器会话而不是单个标签页；一个标签切换角色后，其他标签中的旧角色上下文随即失效。
- 旧标签收到角色上下文变化通知或专用 API 错误后必须停止旧角色写操作并提示刷新，不能继续使用页面缓存提交命令。
- 当前页面存在未提交表单时，切换角色必须先确认；确认后放弃表单、轮换角色上下文与 CSRF，并进入新角色首页，已经提交的业务数据保留。
- API 不得信任 URL、请求体或自定义请求头中由客户端声明的角色、门店或沙箱标识。
- 重置时创建新的标准种子沙箱并切换访客会话，旧沙箱立即失效并等待清理。
- 重置前二次确认并明确说明四个角色的当前演示数据都会清除；成功后返回演示起点，主演示清单归零。
- 使用旧沙箱的浏览器标签收到明确的沙箱失效结果，刷新后进入当前新沙箱。
- 新沙箱记录重置来源事件；旧沙箱及其文件按清理流程删除，不逐表重建原沙箱。
- 所有业务状态变化、配置变更、库存变化、考勤更正、角色切换、导出和重置都写审计事件。
- 被拒绝的越权请求和非法状态跳转写审计事件；普通列表与详情读取不记录。
- 审计事件保存时间、演示人物、角色、沙箱、门店、动作、对象类型与 ID、原因、请求关联 ID 和白名单过滤后的前后差异。
- 审计事件只追加，不编辑或删除；Cookie、令牌、Secret、图片内容和不必要的个人字段不得进入审计。
- 店长查看并导出所属门店审计；总部运营查看并导出当前沙箱全部三店审计。
- 店员只能查看各业务对象的处理事件，顾客不能访问审计后台。

### 仓库与多端边界

- 仓库使用单一 `pnpm workspace`，包含 Web 应用、Hono API、原生小程序、纯领域规则、共享契约和数据库六个逻辑模块。
- 首个 RC 精确锁定 Node.js `24.18.0`、pnpm `9.15.9`、Next.js `16.3.0`、React `19.2.8`、Hono `4.13.1`、`@hono/node-server` `2.1.0`、Drizzle ORM `0.45.2`、Drizzle Kit `0.31.10`、TypeScript `6.0.3` 和 Playwright `1.62.1`。
- 根目录通过版本文件、`packageManager` 字段和唯一 lockfile 固定本地与 CI 工具链；升级依赖必须作为显式变更完成，不能在构建时自动漂移。
- 顾客 H5、员工操作台、店长后台与总部视图位于同一个 Next.js 应用，通过独立路由组和信息架构区分。
- Web 多角色入口共享同源会话与 Web 设计系统，但不能仅靠隐藏按钮实现权限。
- Hono API 是 Web 数据和业务状态的服务端权威。
- 纯 TypeScript 领域包共享状态机、冲突判断、计价、经营日、成长值、体验券和确定性种子规则。
- 共享领域包不能依赖数据库、Node 专用 API、React、Next.js 或微信运行时。
- 小程序通过本地存储适配器执行共享规则，不请求 Web API，也不声称与 Web 状态同步。
- 小程序完整实现顾客侧门店、座位查询、预约、会员、体验券、商品订单、报修、历史和重置，不实现员工或管理后台。
- 小程序只使用本地存储，并可选调用相册或相机选择本地报修图片；不请求位置、联系人、麦克风或电话权限，拒绝图片权限后仍可用文字或内置样例图完成流程。
- 小程序首次启动生成带 schema 版本的本地沙箱；每次业务操作持久化，版本升级执行本地迁移。
- 主动重置恢复当前版本的标准种子；清除本地缓存后重新创建本地沙箱。
- Web 与小程序使用同一确定性种子规范和生成器，通过数据库与本地存储适配器分别落地。
- 两端的人物、门店、异常和主故事保持一致，但实例标识、状态和持久化完全独立。

### Web 数据一致性与 API

- 所有 Web 可变业务记录带 `sandbox_id`，门店级记录同时带 `store_id`；关联对象必须属于同一沙箱。
- 采用共享表中的行级沙箱隔离，不为每个访客创建独立数据库、schema 或表。
- 预约创建在应用层预检查冲突，最终由 Postgres 时间范围排斥约束和事务保证。
- 座位时段重叠与同一顾客跨店时段重叠分别建立数据库约束；事务先推进已过期待确认记录再尝试创建。
- 库存预留、扣减和备件领用使用事务内条件更新或行锁，余额、流水和业务对象一起成功或回滚。
- 预约、商品订单和报修保存当前状态，同时追加不可变业务事件；基础 RC 不使用完整事件溯源重建状态。
- 状态转换、业务事件、副作用和审计事件在同一数据库事务中提交。
- 相关读取或写入先惰性推进已到期预约、订单和沙箱，定时任务兜底执行批量过期及数据库、Blob 清理。
- Web API 使用同源 `/api/v1` JSON 接口。
- EdgeOne 部署配置将 `/api/v1/*` 路由到 Hono Cloud Function，其余 Web 请求进入 Next.js；不依赖 EdgeOne 不支持的 Next.js `redirects` 或 `rewrites`。
- Hono 领域与 HTTP 应用使用标准 Fetch `Request`/`Response` 语义；EdgeOne Cloud Function 只通过单独的薄桥接入口接入，`@hono/node-server` 仅用于本地开发。
- API 核心在部署探针完成前只使用 Node 20 与 Node 24 共同支持的运行时能力，EdgeOne 专用对象和生命周期不能泄漏到领域包或 HTTP 应用核心。
- 创建、模拟支付、取消、状态推进和重置使用明确命令端点，不提供可任意修改状态的通用接口。
- 关键写命令要求幂等键；相同主体、端点和幂等键重复提交相同负载时返回首次结果，负载不同则返回冲突。

### Web 安全、限流与上传

- Web 与 API 保持同源，会话 Cookie 使用 `HttpOnly`、`Secure` 和 `SameSite=Lax`。
- 所有写请求验证 CSRF 令牌与 `Origin`；角色切换和沙箱重置后轮换会话，不开放通配 CORS。
- Postgres RLS 强制限制 `sandbox_id`，应用权限层继续检查角色、门店和具体能力。
- 每次数据库事务显式设置当前沙箱；缺少沙箱上下文时 RLS 默认禁止访问。
- 对象使用不可预测 ID，但所有对象访问仍必须执行沙箱、门店、角色和能力校验。
- 所有输入由服务端 schema 强校验，错误响应包含稳定错误码、安全中文消息、字段问题和请求关联 ID。
- 自由文本只接受规范化后的纯文本并按文本转义展示，拒绝 HTML、控制字符和不符合长度的输入；名称上限六十个字符，取消/验证/更正等原因上限二百个字符，报修描述、解决说明和交接说明上限五百个字符。
- 生产错误不得返回堆栈、SQL、内部路径、Secret 或上游响应正文。
- 匿名演示按 IP、沙箱和操作类型组合限流；写操作、角色切换、重置、导出和上传使用独立额度。
- 超限返回 `429` 和重试时间；限流失败不能产生部分业务副作用。
- 报修上传先由 API 签发绑定沙箱、报修单、文件类型和大小的一次性短期上传意图。
- 图片优先由客户端凭上传意图直传私有隔离区，API 正常请求只承载授权和元数据，不让图片正文穿过 Cloud Function 请求体。
- 完成接口从隔离区读取文件，验证 magic bytes、实际解码结果、尺寸和像素数，并重新编码以移除 EXIF 及其他元数据；只有净化后的文件才进入私有成品区并关联报修单，原隔离文件随即删除。
- 只接受 JPEG、PNG 和 WebP；单图不超过 5 MB，宽高各不超过 4096 像素，总像素不超过一千六百万，成品使用随机对象名与安全响应头。
- 图片只通过短期签名地址读取，不使用原始文件名作为对象名或响应文件名，不进入公开图库、搜索索引或永久分享链接。
- 提交顾客、同店店员和店长以及总部运营可按对象权限查看图片，其他顾客、门店或沙箱不得读取。
- 未完成关联的孤儿文件进入定时清理；若部署探针不支持所需直传能力，适配器回退为 API 代理上传，每次请求只接收一张原始文件，禁止 Base64 和多图批量请求，并保持单图不超过 5 MB。
- 无论直传还是代理都必须经过相同的服务端净化；若部署探针证明目标平台不能在资源限制内安全解码和重新编码，生产演示关闭任意图片上传并使用内置样例图，不能直接保留未经净化的原文件。
- 数据库、Blob、会话和签名密钥只存在于服务端平台 Secret。
- 结构化日志采用字段白名单，只记录请求关联 ID、结果码、耗时和安全业务标识，不记录 Cookie、令牌、完整请求体或图片。
- 公开站点不接入第三方产品分析、广告、指纹识别或会话回放；只使用必要的安全会话 Cookie、CSRF 机制和上述白名单化运维日志。
- 本地开发只提交环境变量示例清单中的变量名、用途和占位值，不提交真实值。

### 实时更新与故障降级

- 服务端使用约二十五秒的短连接发送沙箱级 SSE 失效通知，客户端收到后重新获取相关业务数据，不通过事件流复制完整状态。
- 客户端在连接正常结束后自动重连；SSE 被平台缓冲、提前终止或不可用时退化为短轮询和手动刷新，具体行为在部署探针中验证。
- 数据库或 API 暂时不可用时，Web 显示明确的只读降级模式，使用随构建发布的标准种子快照供浏览。
- 只读降级模式禁用所有写操作，不切换到可写浏览器 Mock，也不伪造服务端保存成功。
- 预约、模拟支付、订单、库存、报修和重置不显示未经服务端确认的乐观成功。
- 写操作超时后使用原幂等键查询或重试，并以服务端最终结果校准页面。
- 沙箱过期或在另一标签被重置时，API 返回专用沙箱失效错误。
- 页面暂存未提交表单并提示用户确认进入新沙箱，不静默刷新或继续向旧沙箱写入。

### 浏览器与可访问性

- 日常开发和主要自动化反馈以开发者本机 Chrome 为主。
- 阶段 D 和 RC 验证 Chrome、Edge、Safari 的目标版本、微信内置浏览器及从 360px 起的顾客 H5 移动端布局。
- 不支持 Internet Explorer。
- RC 最低可访问性要求包括语义标签、完整键盘路径、可见焦点、错误关联、非颜色唯一编码和合格对比度。
- 小程序为交互控件提供无障碍标签及至少 44px 的触控目标。
- 项目不宣称经过正式 WCAG 认证。

### 自动化测试与 CI

- 纯领域规则使用快速单元测试，存储适配器使用契约测试，API、权限与事务使用集成测试，主演示闭环使用 Playwright E2E。
- 本地和 CI 使用真实 Postgres 临时实例运行完整迁移、RLS、时间范围排斥约束、事务和并发测试，不用 SQLite 替代。
- 部署前在独立 Neon 预览环境验证迁移、连接、事务和冷启动，不允许自动化测试直接操作生产数据库。
- PR 快速门禁在 Chromium 运行关键 Web E2E；主分支或 RC 增加 Playwright WebKit。
- RC 使用真实 Chrome、Edge、Safari 和微信内置浏览器完成手工兼容性证据。
- 共享领域包覆盖小程序全部状态规则；小程序适配器测试 schema 迁移、持久化和重置，核心页面运行组件与交互测试。
- RC 使用微信开发者工具和至少一台真机走完小程序主演示。
- 有合适的小程序账号、类目和明确授权时真实尝试一次提审并记录结果；缺少凭据或审核未通过时如实记录，不选择不符合业务的类目，也不把正式审核通过设为基础 RC 门槛。
- 不使用单一全仓覆盖率数字作为完成条件。
- 预约、订单和报修状态转移、权限矩阵、库存事务与全部 P0 风险必须穷举；低风险视觉排列不为覆盖率堆无价值测试。
- CI 合并门禁包括格式检查、lint、TypeScript strict、单元测试、Postgres 集成测试、关键 E2E、三端构建、空库迁移及 seed/reset 验证、依赖漏洞和 Secret 扫描。
- RC tag 只能来自全部门禁通过的提交；部署凭据只存在于受保护环境。

### 性能与并发预算

- 顾客 H5 生产构建在中端移动设备模拟下，关键页面 LCP 不超过 2.5 秒、CLS 不超过 0.1，点击或筛选后的交互响应不超过 200 毫秒。
- 热实例中完整沙箱的事务化物化目标不超过三秒，并单独记录生成行数、事务耗时和失败率。
- Web 性能连续测量五次并报告中位数，不以单次最好结果替代完整样本。
- 生产式预览环境以二十个并发虚拟用户测试：热实例读取接口 p95 不超过 500 毫秒，写接口 p95 不超过一秒，错误率低于 1%。
- 冷启动样本单独报告，不删除、不混入热实例数字，也不据此承诺跨境网络 SLA。
- 同一座位同一时段二十个并发预约只能成功一个。
- 库存为五时，二十个不同幂等请求只能成功预留五份；同一幂等请求并发二十次只产生一个业务对象。
- 旗舰店九十六座座位图在中端移动设备模拟下首次可交互渲染不超过一秒，筛选、缩放或选择反馈不超过 100 毫秒，不出现超过 200 毫秒的主线程长任务。
- 顾客 H5 关键入口初始 JavaScript gzip 后不超过 300 KB，后台按角色和路由拆包。
- 小程序主包控制在部署探针确认的平台上限 80% 以内，非首屏页面进入分包。
- 性能和大陆访问报告记录日期、构建版本、设备、网络、地点、样本数和原始结果。
- 大陆访问覆盖电信、联通、移动、早晚时段、普通浏览器和微信内置浏览器；样本不足时不宣称长期 SLA。

### 部署、迁移与恢复

- 本地、PR 预览和生产使用独立配置与数据；测试、seed 和重置不得访问生产数据。
- 本地使用临时 Postgres；PR 预览使用非生产 EdgeOne/Neon 资源；生产使用独立数据库、Blob 和 Secret。
- PR 创建预览；受保护 `main` 只有在全部 CI 通过后才能合并并自动部署生产。
- RC tag 指向已经验证的生产提交；部署失败时重新部署上一个成功构建。
- EdgeOne Cloud Functions 仅公开 Node 20.x、而 Node 20 已结束上游支持这一矛盾是 RC 发布硬门槛；部署探针必须确认可接受的安全维护运行时，否则迁移 API 到受支持运行时，或由项目所有者明确记录并接受风险后才可公开发布。
- 数据库变更采用前向 expand/contract：先增加兼容结构，再部署兼容代码，最后在后续版本移除旧结构。
- 生产不自动执行破坏性 down migration；失败时回滚应用，并通过新的前向迁移修复 schema 或数据。
- 提供健康检查和结构化日志，跟踪错误率、延迟、冷启动、限流、定时清理、数据库和 Blob 失败。
- 基础 RC 优先使用部署平台自身的日志和指标能力，不强制引入付费 APM。
- 沙箱创建二十四小时后立即不可访问，数据库记录与关联 Blob 在随后二十四小时内物理清理。
- 清理先把沙箱标记为不可访问，再分批删除私有隔离区和成品区 Blob；文件删除完成或进入可重试状态后，按依赖顺序分批删除业务行，避免单个超大删除事务长期锁表。
- 清理完成后只保留不含业务内容、自由文本、人物资料或文件标识的最小删除回执，用于证明清理状态和重试完成时间。
- 未关联报修单的孤儿上传一小时后进入清理。
- 清理失败写入待重试标记，由定时任务和后续请求继续处理；清理失败不能恢复沙箱访问。
- 合成沙箱不做长期业务备份；生产迁移前使用平台可用的数据库分支或快照。
- 严重故障通过重新部署、迁移和确定性 seed 恢复，并保留一次恢复演练记录。
- 首个候选版本标记为 `v1.0.0-rc.1`；Release 包含变更说明、构建复现步骤、测试和访问报告、已知限制、小程序源码与状态以及公开演示入口。
- 发布证据以版本化 Markdown 报告、机器可读结果摘要、截图索引和原始产物校验信息保存在仓库中；大体积视频、浏览器追踪和其他二进制证据作为 GitHub Release 资产，不直接写入 Git 历史。
- RC 制作一段四至六分钟、1080p 的完整业务演示视频，覆盖 Web 四角色与小程序本地模式，并提供中文字幕和英文字幕文件。
- 本地与预览环境通过配置使用临时地址；部署阶段由项目所有者提供最终自定义域名，正式 RC 必须完成该域名的 HTTPS、普通浏览器、微信内置浏览器和大陆三网验证，不能以 EdgeOne 默认项目域名替代。
- 全部 RC 阶段门通过后发布 `v1.0.0`。

### 已查证的平台与版本事实（2026-08-08）

- Node.js 当前 LTS 为 `24.18.0`，Node 20 已于 2026-03-24 结束官方支持。
- EdgeOne Makers 构建环境列出 Node 24，但 Cloud Functions 运行时目前只公开说明为 Node 20.x，未公开精确补丁或切换 22/24 的能力。
- EdgeOne 构建文档明确列出的 pnpm 支持范围为 6 至 9，尚未明确支持 pnpm 10/11。
- EdgeOne 明确支持 Next.js 16，但没有公布具体 patch 兼容矩阵。
- EdgeOne 不支持 Next.js 配置中的 `redirects` 和 `rewrites`，部署路由需要使用平台路由配置或受支持的 Middleware 能力。
- EdgeOne Cloud Functions 默认超时三十秒、可配置十至一百二十秒，请求与响应体上限六 MB，依赖上限 128 MB。
- EdgeOne 没有官方声明 Hono Node Cloud Functions 内建适配；Hono、Neon、SSE、连接复用和流式错误处理仍必须在部署阶段实测。
- 上述事实不等同于基础设施探针已经通过，版本与部署适配仍受 ADR-0001 的延后探针决定约束。

### 角色范围

- 顾客可浏览三店，但只能管理自己的业务记录。
- 店员只操作唯一所属门店。
- 店长只管理唯一所属门店。
- 总部运营覆盖全部三店。
- 基础 RC 不实现一个身份拥有多个业务角色或跨店员工分配。

### 配置权限与历史数据

- 总部运营维护连锁级资料，并可配置全部三家门店，但不能执行到店、商品制作、维修处理、签到或交接等一线业务动作。
- 店长只能配置和经营所属门店，不能读取或修改其他门店受限数据。
- 基础 RC 固定三家门店；总部可修改门店名称、介绍、营业时间和展示信息，但不能新增、删除或停用门店。
- 总部维护连锁级机型档案；店长和总部可在权限范围内配置区域、座位及其机型。
- 座位编号在门店内唯一；停用座位以前必须先处理有效预约和未关闭报修。
- 价格计划按门店、区域、机型、星期和时段适用，相同适用范围不允许出现生效时间重叠。
- 价格变化通过创建新版本并设置未来生效时间完成，不覆盖历史价格计划，已生成价格快照不受影响。
- 已被预约、订单、库存、报修、排班或审计引用的数据只能归档或停用，不能硬删除；未被引用的草稿可以删除。
- 店长可创建、编辑和停用本店背景员工；四个固定演示人物不能停用或删除。
- 员工存在当前或未来班次、未完成报修分派时，必须先处理依赖才能停用。

### 合成经营世界

- 旗舰店：96 座，高峰预约和商品订单密集。
- 标准店：64 座，会员与排班稳定，并包含交接异常。
- 新店：40 座，利用率较低，集中体现缺货、设备故障和备件领用。
- 地域设定为虚构的中国大陆城市，不给出可映射真实场所的详细地址。
- 产品语言为简体中文，货币为人民币，业务时区为 `Asia/Shanghai`。
- 旗舰店全天营业；标准店营业时间为 `10:00–次日 02:00`；新店营业时间为 `12:00–24:00`。
- 三店统一以 06:00 切换经营日，凌晨发生的业务仍归入前一个经营日。

### 沙箱生命周期与演示人物

- Web 沙箱在首次访问时创建，自创建起保留 24 小时。
- 每个沙箱在共享业务表中物化完整独立的三店配置、最近十四个经营日历史、当前积压和主演示人物数据；业务记录不引用其他沙箱的共享历史，也不以预计算数字代替可查询与可导出的事实。
- 沙箱通过确定性生成器和批量 SQL 在单一事务内幂等创建；成功时所有数据同时可见，失败时完全回滚，使用同一创建键重试不能产生重复沙箱。
- 热环境完整创建目标不超过三秒；若超出预算或失败，页面显示可重试状态，不能进入只有部分历史的沙箱。
- 任一角色执行重置时，整个沙箱恢复为标准种子状态。
- 创建与重置默认限制为每个签名访客每小时最多五次、每天最多二十次，并叠加适合共享网络的较宽松 IP 上限；所有阈值通过环境配置调整。
- 活跃沙箱容量采用可配置上限，初始按二百个规划；达到上限时不再创建新沙箱，新访客进入只读标准快照并看到稍后重试提示，已有沙箱继续使用。
- 小程序本地沙箱不采用 Web 的 24 小时 TTL，只能由体验者主动重置或清除本地数据。
- 每个沙箱固定一位主演示顾客、一位店员、一位店长和一位总部运营演示人物。
- 种子中包含其他背景顾客和员工，但公开角色入口不能切换为这些背景人物。
- 每个沙箱记录数据库 schema 版本和种子版本；新部署只为新建或重置后的沙箱使用最新种子，不静默重写现有沙箱历史。
- 应用发布必须至少兼容仍可访问的旧种子二十四小时；破坏兼容性的种子变化必须等待旧沙箱自然失效或通过明确迁移处理。

### 沙箱业务时钟与时间推进

- 每个 Web 沙箱拥有四个角色共享的沙箱业务时钟，初始锚定创建时的上海真实时间并按真实速度正常流逝。
- 页面提供明确标注的沙箱级演示时间工具；它不属于顾客、店员、店长或总部运营权限，持有当前沙箱的访客切换到任意角色时都可以使用。
- 时间只能通过“下一事件”或“+30 分钟”向前推进，不能回拨或任意输入日期；单个沙箱相对初始锚点累计最多推进二十四小时，之后通过重置重新开始。
- 每次演示时间推进写入审计事件，并向同一沙箱的其他标签发送失效通知。
- 预约、订单、排班、考勤和交接等业务时间使用沙箱业务时钟；沙箱二十四小时寿命、会话、CSRF、限流、幂等保留、上传凭证、孤儿文件与物理清理使用真实服务器时间。
- 业务事件保存沙箱业务发生时间；审计事件同时保存业务发生时间与不可变的服务器记录时间，不能用推进后的时间伪造安全或清理记录。
- 推进命令在服务端事务中更新时钟并处理跨越的到期事件；同一时刻依次处理待确认预约与待支付订单过期、预约爽约、使用中预约自动完成、考勤缺勤和交接异常。
- 任一到期处理失败时整个推进事务回滚，不能暴露“时钟已前进但状态未推进”的中间结果；重复提交使用同一幂等键返回首次结果。

### 主演示引导

- Web 提供可收起并可重新打开的跨角色主演示清单，覆盖预约、模拟支付、到店、使用、商品订单、报修、备件、验证、看板、导出和重置。
- 清单进度从主演示顾客及其关联业务对象、业务事件和库存流水推导，不能由前端手工勾选，也不能因为种子中的背景历史记录而提前完成。
- 切换角色或重新打开页面后，从服务端权威状态恢复相同进度；沙箱重置后清单回到起点。
- 小程序提供适配本地顾客流程的引导，但不显示 Web 员工、店长或总部步骤，也不声称能推进 Web 清单。

### 时间种子与会员

- 重置时以当前上海时间作为场景锚点，历史和未来事件采用确定性的相对时间偏移。
- 自动化测试注入固定时钟；同一随机种子和场景锚点必须生成相同结果。
- 每位顾客拥有一份连锁级会员档案；等级和成长值三店共享。
- 体验券可以限制适用门店、商品或时段，但不可储值、兑付或折现。
- 会员设置三级，累计成长值门槛为 `0 / 500 / 1500`；成长值终身累计、不清零且不降级。
- 三级会员正式名称依次为青铜、白银和黄金。
- 等级本身不自动改变预约期限、预约时长、价格或角色权限。
- 已完成预约和已完成商品订单，按体验券减免后的最终模拟金额每满一元获得一点成长值。
- 取消、过期和订单损耗不产生成长值，后台不能手工调整成长值。
- 体验券只支持固定金额减免，每张券明确用于预约或商品订单。
- 体验券可限制门店、商品分类、价格时段、最低金额和有效期；每笔交易最多使用一张。
- 减免后的模拟金额最低为零，体验券不能叠加、折现、转让或形成余额。
- 创建待确认预约或待模拟支付订单时占用体验券，模拟支付后标记已使用。
- 预约在使用前取消或过期、订单在制作前取消时，体验券恢复可用；预约开始使用或订单开始制作后不再恢复。
- 等级门槛、成长规则和体验券来自固定合成配置，基础 RC 不提供批量发券或券模板管理后台。

### 经营看板与导出

- 模拟营业额只统计已完成预约和已完成商品订单的最终模拟金额；取消、过期和未完成交易不计入。
- 订单损耗数量和金额影响单独展示，不混入模拟营业额。
- 同时展示运营座位利用率和维护不可用率：前者使用正常可经营座位分钟数作分母，后者使用营业座位分钟数作分母。
- 默认日期范围为当前经营日和最近七个经营日，并支持自定义区间。
- 合成种子包含完整的最近十四个经营日历史，所有按日统计使用 06:00 经营日边界。
- 预约、订单、库存流水、报修、排班和审计分别导出当前筛选结果。
- 导出使用带 UTF-8 BOM 的 CSV，基础 RC 不生成 `.xlsx` 文件。
- 总部并列比较三店的模拟营业额、座位利用率、维护不可用率、订单完成率、库存告警、考勤和交接异常。
- 不生成综合分、最佳门店排名或使用硬编码图表；全部指标从当前沙箱业务记录计算。
- 预约完成后，最终未退款的半小时价格片段分别归入片段所在经营日；跨越 06:00 的预约可以拆分到两个经营日。
- 商品订单的最终模拟金额全部归入订单完成时所在经营日。
- 订单完成率为已完成订单除以所有已经进入终态且完成过模拟支付的订单；未支付过期单和仍在处理的订单不进入分母。
- 未完成商品订单作为当前积压单独展示。
- 报修指标包括按优先级统计的未关闭数量、从新建到关闭的中位处理时长以及维护分钟数。
- 考勤指标分别展示准时、迟到和缺勤；交接班展示异常数量，不生成综合运营分或 SLA 达标率。

### 主演示与预约边界

- 主演示业务闭环发生在全天营业的旗舰店；标准店提供稳定经营与交接异常背景，新店提供预置的缺货和维修异常。
- 座位只持久记录正常或维护中的运营状态。
- 指定时段内的空闲、已预留和使用中是依据座位运营状态、预约及当前时间计算出的座位可订性，不是永久座位状态。
- 一条预约只对应一位顾客、一个明确座位和一段连续时间，不支持区域自动分配、多座位或组队包座。
- 预约开始时间按 30 分钟对齐，最短 1 小时、最长 8 小时，可预约未来 7 天。
- 同一顾客在全部门店范围内不能拥有时间重叠的有效预约。
- 预约不得跨越门店的非营业时间；全天营业的旗舰店可以跨午夜预约。
- 基础 RC 不支持店员创建现场预约或绕过冲突检查；店员只处理顾客已经创建的预约。
- 旗舰店提供明确标注的“立即预约”：开始时间取当前半小时片段起点，当前片段按完整片段计费，创建后可以立即办理到店和使用。
- 普通未来预约仍按半小时起点选择；立即预约不改变最短一小时、最长八小时和冲突规则。

### 门店座位、机型与价格

- 总部机型档案分为标准型、竞技型和旗舰型，不绑定具体 CPU 或 GPU 品牌型号。
- 标准型描述为 1080p/144Hz 体验，竞技型为 2K/180Hz，旗舰型为 2K/240Hz。
- 旗舰店九十六座：四十个标准型、四十个竞技型、十六个旗舰型。
- 标准店六十四座：三十二个标准型、二十四个竞技型、八个旗舰型。
- 新店四十座：二十四个标准型、十二个竞技型、四个旗舰型。
- 每小时基础价按标准型、竞技型、旗舰型排列：旗舰店为 `10/15/22` 元，标准店为 `8/12/18` 元，新店为 `7/10/15` 元。
- 周一至周五 06:00–18:00 使用基础价，18:00–24:00 乘 `1.20`，00:00–06:00 乘 `0.90`。
- 周六与周日全部营业时段统一乘 `1.15`，不再叠加工作日深夜或晚间系数。
- 价格计划生成明确的半小时金额并以整数分存储和计算，不使用二进制浮点金额。

### 合成目录、人员与主演示故事

- 连锁级商品目录包含十二个虚构商品：四种饮品、四种零食、两种简餐和两种日用补给。
- 商品不使用真实品牌，不包含酒类、烟草、游戏充值或处方相关内容。
- 维修备件包含键盘、鼠标、耳机、显示线、网线、电源、散热风扇和内存八类，使用虚构规格且不记录真实采购成本。
- 旗舰店包含十四名店员和两名店长，标准店包含九名店员和一名店长，新店包含六名店员和一名店长。
- 总部另有三名背景运营人员；四个公开演示人物仍按受保护人物规则固定。
- 最近十四个经营日的数据按确定性目标区间生成：旗舰店晚高峰座位利用率约 80%～90%，标准店约 55%～70%，新店约 30%～45%。
- 周末经营量高于工作日，历史记录包含完整终态，并保留少量用于操作台展示的当前积压。
- 主演示顾客为白银会员，初始成长值 860，拥有一张预约固定金额减免券和一张商品固定金额减免券。
- 主演示顾客在重置后没有未完成预约或商品订单，可以从旗舰店空闲座位发起立即预约。
- 主演示固定创建一笔竞技型座位的两小时立即预约，随后完成到店、开始使用以及商品订单创建和模拟支付。
- 访客把沙箱业务时钟推进三十分钟后提交“耳机右声道无声”报修。
- 店员分派并开始处理后，预约因设备故障提前完成，已开始的价格片段计费、后续完整片段按既定规则模拟退款；店员领用一副替换耳机。
- 维修验证成功后关闭报修、恢复座位，店长和总部看板随业务记录更新。

### 预约生命周期与计价

- 创建待确认预约时必须原子检查冲突并占用对应座位时段，保留十分钟。
- 模拟支付成功后，预约从待确认变为已确认；待确认超过十分钟后由系统变为已过期并释放占用。
- 顾客可在预约开始前取消待确认或已确认预约。
- 店员和店长可在预约进入使用中以前带原因取消预约。
- 已确认预约在计划开始十五分钟后仍未到店，由系统变为已过期。
- 取消或过期会释放座位占用及尚未使用的体验券；预约完成以前不发放成长值。
- 预约开始前三十分钟至开始后十五分钟，店员可以将已确认预约标记为已到店。
- 已到店预约只能在计划开始时间到达后进入使用中。
- 店员可以提前结束使用；到达计划结束时间仍处于使用中的预约由系统自动完成。
- 价格按半小时片段计算；每个片段使用其所在时段、区域和机型对应的价格计划。
- 创建待确认预约时保存价格明细快照，后续价格配置变化不影响已有预约。
- 基础 RC 不支持直接改期或换座；顾客必须取消原预约后重新创建。
- 未完成模拟支付的预约取消或过期时，不创建模拟退款记录。
- 已确认预约在使用前取消、过期或因座位维护终止时，全额模拟退款并恢复体验券。
- 顾客主动提前结束使用不产生模拟退款。
- 因设备故障中断使用时，当前不足半小时的价格片段照常计费，后续完整半小时片段模拟退款；体验券不恢复。

### 商品目录、订单与库存

- 顾客只有在目标门店拥有已到店或使用中的预约时才能下单；订单关联该预约和座位，履约方式仅为柜台取货。
- 总部维护连锁级商品资料；各门店分别配置上架状态、售价和库存。
- 可销售商品和维修备件共用门店级库存项目与库存流水，通过库存类别和业务原因区分。
- 创建待模拟支付订单时，必须以整单为单位原子检查并预留库存；任一行库存不足则整单失败。
- 待模拟支付订单保留十分钟，超时后变为已过期并释放全部库存预留。
- 关联预约在订单完成模拟支付前进入终态时，待模拟支付订单立即取消并释放库存预留，之后不得继续模拟支付。
- 模拟支付后，订单进入已模拟支付；店员依次推进制作中、待取和已完成。
- 关联预约在订单完成模拟支付后取消、过期或因设备故障提前完成，不自动取消该订单；订单继续按柜台取货流程履约，顾客或店员仍可按订单自身规则取消。
- 制作中与待取阶段继续占用库存；订单完成时库存按销售扣减。
- 顾客只能在制作开始前取消订单；店员可在完成以前带原因取消。
- 制作开始前取消会释放库存预留；制作开始后取消会将预留库存按损耗扣减。
- 不支持部分成功、缺货项自动删除、部分领取或部分取消；库存和订单变更必须整单原子完成。
- 创建订单时保存商品名称、单价、数量、优惠和总额快照；后续商品改名、改价或下架不修改历史订单。
- 商品和备件均按整数件管理；账面库存、预留库存和可用库存不得为负，预留不得超过账面库存。
- 店员可查看库存，只能通过订单或报修执行相应库存操作。
- 店长负责手工入库、盘点、门店商品配置和低库存阈值。
- 总部运营可比较三店库存并维护总部商品资料，但不能直接修改门店库存。
- 手工入库创建正向流水；盘点输入实际数量并创建差额调整流水，必须记录操作者和原因。
- 历史库存流水不可编辑或删除；错误通过新的补偿流水修正。
- 每个门店库存项目拥有独立告警阈值；可用库存小于或等于阈值时自动告警，超过阈值后自动解除。
- 基础 RC 不支持跨店调拨、供应商、采购订单、成本批次、税额或毛利核算。
- 经营看板只展示预约、模拟销售、库存数量、损耗及运营效率，不展示伪造的利润指标。
- 未完成模拟支付的订单取消或过期时，不创建模拟退款记录。
- 已模拟支付订单在制作前取消时全额模拟退款并恢复体验券。
- 制作开始后取消仍全额模拟退款，但体验券不恢复，关联库存按订单损耗扣减。

### 报修与座位维护

- 顾客提交设备故障时直接创建新建报修单；店员也可以主动创建，不设置独立故障报告实体。
- 基础 RC 的报修单必须关联一个座位及其机型，不支持非座位设施报修。
- 同一座位同时最多存在一张未关闭报修单；重复提交时返回并展示已有报修单。
- 新建转为已分派时必须记录处理人和优先级。
- 处理人或店长可以将已分派报修单推进为处理中。
- 从处理中进入待验证以前必须提交解决说明。
- 同店店员或店长记录验证成功后关闭报修单；验证失败则退回处理中并记录原因。
- 新建和已分派状态不改变座位运营状态。
- 进入处理中时，座位必须在同一事务中变为维护中。
- 若关联座位存在已到店预约，则取消预约并记录设备故障原因；若存在使用中预约，则提前完成并记录设备故障中断原因。
- 只有处理中的报修单可以领用备件；库存扣减、备件使用记录、库存流水和报修事件必须原子成功或失败。
- 报修关闭前可以退回未使用备件，退回数量不得超过该报修单尚未退回的领用数量。
- 座位进入维护中时，原子取消从当前时间起关联该座位的全部待确认、已确认和已到店预约；使用中预约提前完成。
- 维护引起的预约终止必须记录设备维护原因、释放体验券并写入预约事件，不自动换座。
- 待验证期间座位保持维护中；验证成功时，关闭报修单与座位恢复正常必须原子完成。
- 验证失败时，报修单退回处理中，座位继续维护。
- 顾客和店员可为报修单上传最多三张 JPEG、PNG 或 WebP 图片，每张不超过 5 MB。
- 上传文件必须验证声明类型、扩展名和 magic bytes，只能在当前沙箱内授权读取，并随沙箱过期清理。
- Blob 上传失败时，报修流程仍可继续，并允许使用随应用发布的内置样例图片。
- 报修优先级分为普通、较高和紧急，只影响排序与告警；基础 RC 不实现 SLA 计时或升级。
- 顾客只能看到公开状态、公开处理说明和验证结果；内部笔记、分派备注及库存成本只对员工角色可见。
- 已关闭报修不可重新打开；后续故障必须创建新的报修单。

### 员工、排班与交接班

- 每名员工固定属于一家门店，并拥有店员或店长角色；基础 RC 不支持跨店任职或借调。
- 店长管理所属门店的员工与排班；总部运营只查看三店人员和排班汇总。
- 班次开始和结束时间按三十分钟对齐，时长为四至十二小时，允许跨午夜。
- 同一员工的班次不得重叠；门店人员覆盖不足只产生告警，不阻止保存排班。
- 签到为明确标注的模拟行为，不使用定位、人脸、门禁或其他真实考勤连接器。
- 员工可从班次开始前三十分钟起签到；班次开始后签到标记迟到，班次结束仍未签到标记缺勤。
- 签到后由员工手动签退，系统不自动伪造签退时间。
- 尚未签到的未来班次可修改或取消；签到后的班次时间不可直接修改。
- 店长通过带原因的考勤更正记录修正迟到、缺勤或签退时间，原始记录保留。
- 交班人提交时，系统保存未完成预约、商品订单、报修和库存告警快照，并允许追加文字说明。
- 交接提交后不可编辑；交班人提交后即可签退，不必等待接班人确认。
- 接班人可以随后确认交接；班次结束三十分钟仍未提交、迟交或长期未确认都会产生交接异常。
- 交接内容不包含现金盘点或真实支付对账。

## Testing Decisions

### 测试原则与接缝

- 好测试只验证调用者可观察的行为、持久状态、业务事件、副作用、权限结果和错误契约，不绑定私有函数、SQL 语句顺序、组件内部状态或实现细节。
- 测试优先使用能够覆盖最多真实协作边界的最高接缝；只有在反馈速度、运行时差异或失败定位确实需要时才下沉一层。
- 当前仓库尚无业务实现和既有测试先例，因此不存在可复用的业务测试接缝；本规格建立五个最小必要接缝，分别对应纯领域、持久化、服务端、Web 浏览器和小程序运行时边界。
- 接缝一是纯领域规则：以公开命令、状态和计算结果验证状态机、经营日、计价、成长值、体验券、指标、沙箱业务时钟和确定性种子。
- 接缝二是存储适配器契约：同一套外部行为契约分别运行于 Postgres 适配器和小程序本地存储适配器，防止两端规则漂移。
- 接缝三是 Hono API 与真实 Postgres 集成：从 HTTP 请求进入，经权限、RLS、事务和约束到响应与持久结果，是授权、一致性和并发测试的主要接缝。
- 接缝四是 Web 浏览器主演示 E2E：从公开入口开始顺序切换四个角色，验证用户实际能完成纵向闭环，而不是单独测试每个页面内部实现。
- 接缝五是小程序本地运行时：以共享领域规则、存储适配器、核心组件、微信开发者工具和至少一台真机验证顾客流程。
- 测试使用可注入的固定上海业务时钟、真实服务器时钟和确定性随机种子；等待真实十分钟、数小时或跨日不是可接受测试方式。
- 不以单一全仓覆盖率数字作为完成标准；预约、订单、报修状态机、权限矩阵、库存事务和全部 P0 风险要求穷举，低风险视觉排列不堆砌无价值断言。

### 领域与契约测试

- 穷举预约合法与非法状态转换、十分钟占用、到店窗口、十五分钟爽约、自动完成、取消和设备故障提前结束。
- 验证立即预约从当前半小时片段起点计费，普通预约按半小时对齐，一至八小时边界和未来七天边界准确。
- 验证工作日三个价格时段、周末系数、跨午夜和跨 06:00 经营日的半小时整数分计价。
- 验证价格快照不受后续价格计划、区域或机型变化影响，重叠价格版本被拒绝。
- 验证会员等级门槛、成长值取整、终身不降级以及取消、过期、损耗不产生成长值。
- 验证体验券排他占用、模拟支付后使用、各取消边界的恢复或不恢复、最低金额和适用范围。
- 穷举商品订单状态、整单库存预留、制作前释放、制作后损耗、完成销售扣减及关联预约终止行为。
- 验证账面、预留和可用库存恒等式，所有数量保持整数且不为负，补偿流水不修改原流水。
- 穷举报修新建、已分派、处理中、待验证、已关闭与验证失败路径，验证同座位最多一张未关闭报修。
- 验证进入处理中、座位维护、受影响预约、模拟退款、备件领退和业务事件的原子联动。
- 验证班次对齐、时长、重叠、迟到、缺勤、签退、考勤更正、交接快照与交接异常规则。
- 验证运营座位利用率、维护不可用率、模拟营业额、订单完成率、报修中位时长和经营日归属公式。
- 验证 Web 和小程序同一逻辑种子产生等价人物、门店、异常和故事，但持久化 ID 与状态彼此独立。
- 验证小程序本地 schema 迁移、重启持久化、清缓存重建和主动重置契约。

### API、数据库与安全测试

- 本地和 CI 使用真实临时 Postgres 执行空库迁移、RLS、时间范围排斥约束、索引、事务和 seed/reset，不以 SQLite 或内存数据库替代。
- 并发二十次创建同座位同时段预约只能成功一次；同一顾客跨门店重叠预约也只能保留一个合法结果。
- 库存为五时，二十个不同幂等请求只能成功预留五份；同一幂等请求并发二十次只产生一个订单及一组副作用。
- 备件不足、流水写入失败或报修事件写入失败时，报修、库存余额和座位状态全部回滚。
- 对顾客、店员、店长和总部运营的每项能力运行允许与拒绝测试，覆盖跨门店、跨沙箱、对象枚举和旧角色上下文。
- 缺少 RLS 沙箱上下文时默认拒绝；伪造 URL、请求体、请求头中的角色、门店和沙箱标识不能扩大权限。
- 非法状态跳转、越权请求和关键失败写入过滤后的审计事件；普通读取不产生审计噪声。
- 验证相同幂等键和相同负载返回首次结果，不同负载返回冲突，超时重试不重复副作用。
- 验证 CSRF、Origin、SameSite、安全 Cookie、会话轮换、旧标签失效、限流与稳定错误码。
- 验证自由文本长度、控制字符、HTML、输出转义和日志白名单，错误响应不泄露堆栈、SQL、Secret 或上游正文。
- 验证图片上传意图范围、文件类型、magic bytes、实际解码、尺寸、像素数、重新编码、元数据移除、签名读取和跨沙箱拒绝。
- 验证图片直传与单图代理两种运输适配器执行相同净化；无法净化时只允许样例图而不保留原文件。
- 验证沙箱业务时钟推进的固定顺序和事务回滚，真实服务器时间控制的 TTL、会话、限流和清理不受推进影响。
- 验证完整沙箱在单一幂等事务中生成，部分失败不暴露数据；相同随机种子与场景锚点可复现。
- 验证旧种子在二十四小时兼容期内继续运行，新建或重置才采用最新种子。
- 验证过期沙箱立即不可访问、Blob 先于业务行分批清理、失败可重试且最终只保留最小删除回执。
- 验证 CSV 列、筛选、排序、金额、经营日和 UTF-8 BOM 与页面结果一致，越权角色不能导出受限数据。

### Web、小程序与发布验证

- Playwright 主路径从新访客入口创建沙箱，完成两小时竞技型立即预约、模拟支付、到店、使用、商品订单、推进三十分钟、耳机报修、维修、分段模拟退款、备件领用、验证、看板、导出和重置。
- Web E2E 验证清单进度来自真实业务事件，角色切换保持同一沙箱，重置后旧标签和旧对象失效。
- Web E2E 覆盖空、错、慢、拒绝、超时、重复提交、表单保留、只读降级、SSE 重连、轮询降级和手动刷新。
- PR 快速门禁在 Chromium 运行关键 E2E，主分支与 RC 增加 Playwright WebKit；RC 另以真实 Chrome、Edge、Safari 和微信内置浏览器保存手工证据。
- 可访问性验证覆盖语义标签、键盘完整路径、可见焦点、错误关联、对比度、非颜色唯一编码、小程序无障碍标签和至少 44px 触控目标。
- 小程序运行共享领域规则与本地适配器测试，核心页面执行组件和交互测试，并在微信开发者工具与至少一台真机走完本地主演示。
- 顾客 H5 在中端移动设备模拟下连续测量五次，LCP 不超过 2.5 秒、CLS 不超过 0.1、交互反馈不超过 200 毫秒，以中位数报告。
- 热实例 API 以二十个并发虚拟用户验证读取 p95 不超过 500 毫秒、写入 p95 不超过一秒、错误率低于 1%；冷启动独立报告。
- 热实例完整沙箱物化不超过三秒；旗舰店九十六座首次可交互渲染不超过一秒，筛选、缩放和选择反馈不超过 100 毫秒，避免超过 200 毫秒长任务。
- 顾客 H5 初始 JavaScript gzip 后不超过 300 KB，后台按角色和路由拆包；小程序主包控制在探针确认上限的 80% 内。
- 部署探针验证 EdgeOne 构建、Cloud Function、Hono 适配、Neon 连接与事务、Blob 净化、SSE、清理、自定义域名、HTTPS 和回滚。
- 大陆访问验证覆盖电信、联通、移动、早晚时段、普通浏览器和微信内置浏览器，并记录构建版本、日期、地点、设备、网络、样本与原始结果。
- CI 合并门禁包括格式、lint、TypeScript strict、领域与契约测试、真实 Postgres 集成、关键 E2E、Web/API/小程序构建、空库迁移、seed/reset、依赖漏洞和 Secret 扫描。
- 只有全部门禁通过的提交可以合并主分支和创建 RC tag；自动化测试不得连接或修改生产数据库。

## Out of Scope

- 不服务真实门店，不产生真实预约、商品履约、维修承诺或经营结算。
- 不支持多个经营方、多租户入驻、门店加盟关系或动态新增经营方。
- 不实现真实注册、密码、短信验证码、员工邀请、单点登录或身份找回。
- 不收集身份证、人脸、真实姓名、电话、邮箱、详细地址、真实上网记录或未成年人资料。
- 不建立未成年人账户或真实预约，也不实现年龄核验流程。
- 不接入真实微信支付、银行卡、充值、储值、退款、结算、发票、税务或财务对账。
- 不接入公安实名、门禁、定位、人脸、机器开关机、硬件遥测或真实考勤系统。
- 不实现游戏充值、赛事、社交、押注、博彩、酒类、烟草或处方相关商品。
- 不实现真实利润、采购成本、毛利、供应商、采购订单、成本批次或税额核算。
- 不支持动态增删三家门店；基础 RC 只允许修改固定门店资料。
- 不支持一个身份拥有多个业务角色、跨店员工任职、借调或总部继承全部一线权限。
- 不支持店员创建现场预约、区域自动分配、组队包座、多座位预约或不连续时段。
- 不支持预约直接改期、换座或自动迁移；需要取消后重新预约。
- 不支持订单部分成功、缺货项自动删除、部分领取、部分取消、配送或外卖。
- 不支持跨店库存调拨，也不允许总部直接修改门店库存数量。
- 不支持非座位设施报修、同座位多张并行报修、关闭后重开或正式 SLA 承诺。
- 不实现现金盘点、真实交接对账或自动伪造签退时间。
- 不提供成长值手工调整、批量发券、券模板后台、储值余额、返现或体验券转让。
- 不提供复合门店评分、最佳门店排名、硬编码看板数字或长期网络 SLA 声明。
- 不生成原生 Excel 工作簿；导出范围为 Excel 友好的 UTF-8 BOM CSV。
- 不让小程序请求自建 Web API，也不宣称小程序本地沙箱与 Web 沙箱同步。
- 不在小程序实现店员、店长或总部运营后台。
- 不请求小程序位置、联系人、麦克风或电话权限。
- 不接入第三方产品分析、广告、指纹识别或会话回放。
- 不公开报修图片，不建立永久分享链接、公开图库或搜索索引。
- 不以完整事件溯源重放全部状态；业务表保存当前状态并追加事件。
- 不为每个沙箱创建独立数据库、schema 或表。
- 不使用 SQLite 模拟 Postgres 约束和事务。
- 不依赖破坏性 down migration 作为生产回滚方案。
- 不支持 Internet Explorer，也不宣称完成正式 WCAG 认证。
- 不把微信正式审核通过设为基础 RC 完成条件，不通过错误类目规避审核要求。
- 不把 EdgeOne 默认项目域名作为正式 RC 的公开地址。
- 不在基础设施探针通过前声称目标云运行时、SSE、图片处理或大陆访问已经验收。
