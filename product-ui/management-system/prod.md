## 1. 文档定位

本文档把[基础 RC 规格](../../.scratch/jingshu-basic-rc/spec.md)转译为 Web 管理系统的正式设计输入，覆盖公开访客进入演示后在同一沙箱内依次切换店员、店长和总部运营的完整体验。顾客 Web H5 是跨角色故事的必要入口，但其顾客页面结构由[小程序产品设计说明](../miniprogram/prod.md)负责；本文档负责 Web 沙箱、角色切换和管理侧页面。

设计与实现发生冲突时，按以下顺序处理：

1. [领域词汇](../../CONTEXT.md)决定业务名词及其含义。
2. `spec.md` 和已接受 ADR 决定状态机、权限、不变量及数据边界。
3. 本文档决定 Web 信息架构、页面职责、角色视图和设计交付范围。
4. 视觉稿决定品牌表达与组件外观，不得通过隐藏按钮或视觉层级改变权限。

必须按条件查阅的 ADR：

- 设计经营日筛选、跨午夜排班或日趋势时，查阅 [ADR-0002](../../docs/adr/0002-business-day-starts-at-0600.md) 与 [ADR-0009](../../docs/adr/0009-attribute-reservation-revenue-by-price-segment.md)。
- 设计座位、价格、库存、报修联动时，分别查阅 [ADR-0003](../../docs/adr/0003-derive-seat-availability-by-time-range.md)、[ADR-0004](../../docs/adr/0004-snapshot-reservation-price-on-creation.md)、[ADR-0005](../../docs/adr/0005-unified-inventory-ledger.md) 与 [ADR-0006](../../docs/adr/0006-repair-processing-controls-seat-maintenance.md)。
- 设计角色入口、切换、门店范围或总部权限时，查阅 [ADR-0010](../../docs/adr/0010-server-issued-public-role-context.md)、[ADR-0012](../../docs/adr/0012-headquarters-configures-but-does-not-operate-stores.md) 与 [ADR-0018](../../docs/adr/0018-rls-for-sandbox-application-for-role-scope.md)。
- 设计重置、演示时间与实时刷新时，查阅 [ADR-0011](../../docs/adr/0011-reset-by-rotating-sandbox.md)、[ADR-0020](../../docs/adr/0020-sse-invalidation-with-polling-fallback.md) 与 [ADR-0023](../../docs/adr/0023-separate-sandbox-business-time-from-wall-clock.md)。

## 2. 设计目标

管理系统要证明竞枢不是一组孤立后台页面，而是同一业务对象跨角色、跨门店、跨状态变化的经营协同系统。第一次体验的访客无需开发者陪同，应能完成并理解：

1. 在创建沙箱前了解产品、演示边界和四个公开角色。
2. 以顾客 Web H5 创建旗舰店两小时立即预约并完成模拟支付。
3. 切换店员办理到店、开始使用、处理商品订单和设备报修。
4. 看到报修进入处理中时座位维护、受影响预约、模拟退款和备件库存原子联动。
5. 切换店长验证维修、管理单店经营，并查看审计证据。
6. 切换总部运营比较三店经营结果、查看连锁配置并导出当前筛选数据。
7. 使用沙箱业务时钟推进期限，最后重置整个四角色故事。

成功标准是角色职责、业务状态和因果证据都清晰可见；不以“图表数量多”或“后台模块多”作为完成标准。

## 3. 产品与设计范围

### 3.1 本设计包包含

- 创建沙箱前的公开产品入口和四角色说明。
- Web 沙箱初始化、容量不足只读快照、服务故障只读降级。
- 共享演示壳：演示数据标识、角色切换、主演示清单、沙箱业务时钟、重置和刷新状态。
- 店员所属门店的现场工作台、预约、商品订单、报修、库存、班次和交接班。
- 店长所属门店的经营看板、现场业务、配置、库存、员工、排班、考勤更正、交接异常、审计与导出。
- 总部运营的三店比较、连锁目录、全部固定门店配置、人员排班汇总、审计与导出。
- 顾客 Web H5 的接入、角色切换和跨角色故事衔接。

### 3.2 不属于本设计包

- 真实注册、密码、员工邀请、单点登录或身份找回。
- 多经营方、多租户、加盟关系或新增第四家门店。
- 真实支付、退款、充值、结算、发票、税务、成本和利润。
- 真实门禁、定位、人脸、机器控制、硬件遥测或真实考勤连接器。
- 供应商、采购订单、跨店调拨、配送、部分订单或非座位设施报修。
- 总部替门店执行到店、制作、维修、签到或交接。
- 综合门店评分、最佳门店排名、伪造利润指标或硬编码图表数字。
- 独立的手机端管理后台；管理侧以桌面和横向平板为主要工作面。

### 3.3 必须持续显示的演示边界

- 所有角色页持续显示“演示数据”。
- 所有模拟支付入口、确认和结果明确显示“不扣款”。
- 所有虚构门店和人员不得包装为真实经营主体。
- 自由文本提示不要填写真实个人信息。
- 当前角色、演示人物和门店范围在管理壳中始终可查。
- Web 沙箱自创建起保留 24 小时；复制公开地址不会分享当前可写状态，其他访客会得到自己的沙箱。

## 4. 角色与权限

### 4.1 角色定义

| 角色 | 数据范围 | 主要职责 | 明确限制 |
| --- | --- | --- | --- |
| 顾客 | 可浏览三店；仅管理自己的业务记录 | 预约、商品订单、会员权益、报修 | 不进入员工或配置后台 |
| 店员 | 唯一所属门店 | 到店、使用、商品履约、报修、备件、班次、交接 | 不直接调整库存，不读取其他门店 |
| 店长 | 唯一所属门店 | 单店经营、配置、库存、员工排班、考勤、工单、审计 | 不读取或修改其他门店受限数据 |
| 总部运营 | 全部固定三店 | 连锁资料、三店配置、横向比较、汇总、全沙箱审计 | 不继承一线动作，不直接改库存或替门店排班 |

一个演示人物只拥有一个业务角色；员工固定属于一家门店，不支持跨店任职或借调。

### 4.2 能力矩阵

| 能力 | 店员 | 店长 | 总部运营 |
| --- | :---: | :---: | :---: |
| 查看本店今日预约、订单、报修 | ✓ | ✓ | 汇总/配置视角 |
| 办理到店、开始/结束使用、带原因取消 | ✓ | ✓ | — |
| 推进商品订单、带原因取消 | ✓ | ✓ | — |
| 创建/分派/处理/验证本店报修 | ✓ | ✓ | — |
| 处理中领用与退回备件 | ✓ | ✓ | — |
| 查看账面/预留/可用库存 | ✓ | ✓ | 三店比较 |
| 手工入库、盘点、补偿流水 | — | ✓ | — |
| 配置门店商品上架与售价 | — | ✓ | ✓，覆盖固定三店 |
| 配置低库存阈值 | — | ✓ | — |
| 维护本店区域、座位、价格 | — | ✓ | ✓，覆盖三店 |
| 维护连锁商品与机型档案 | — | — | ✓ |
| 管理本店员工与排班 | — | ✓ | 只看三店汇总 |
| 模拟签到/签退、提交/确认交接 | 本人 | 可作为员工执行 | — |
| 追加考勤更正 | — | ✓ | — |
| 查看经营看板 | 现场摘要 | 本店 | 三店比较 |
| 查看/导出审计 | — | 本店 | 全部三店 |
| 导出业务列表 | 按页面授权 | 本店 | 全部三店 |

界面不能用“总部 = 超级管理员”的表达，也不能因为总部导航层级更高而显示一线按钮。

## 5. 共享演示壳

### 5.1 创建沙箱前的公开入口

公开入口在任何沙箱创建前展示：

1. 产品用途：电竞场馆预约与运营协同演示。
2. 边界：虚构数据、无需注册、不发生真实支付、不接入真实设备。
3. 四个角色卡及其职责，推荐从顾客开始。
4. 主演示概览和预计步骤，不承诺真实门店服务。
5. 只读了解入口或辅助说明。

只有访客选择角色后才创建沙箱。页面打开、爬虫访问或只读浏览不得表现为已经创建可写业务数据。

页面启动时先确认当前浏览器是否已有角色上下文。只有服务端明确返回上下文不存在或已终止时才显示可写角色入口；网络、数据库或角色服务瞬时故障时必须阻止新沙箱创建，并提供同一检查的安全重试。若签名会话仍有效但版本陈旧，页面直接按服务端当前角色规范化恢复，不要求已丢失的页面版本，也不开放新沙箱创建。

### 5.2 角色页全局框架

桌面端全局框架包含：

- 左侧角色化一级导航。
- 顶部当前演示人物、业务角色、门店范围。
- 持续可见的“演示数据”标识。
- 当前沙箱到期时间或可查看的生命周期说明。
- 沙箱业务时钟与演示时间工具入口。
- 主演示清单入口及当前完成度。
- 角色切换与沙箱重置入口。
- 数据刷新状态；SSE 不可用时显示轮询或手动刷新状态。

角色切换、演示时间与重置属于共享演示壳，不放进任一角色的业务导航中。

### 5.3 角色切换

- 切换器同时说明目标角色、目标演示人物和门店范围。
- 页面有未提交表单时，先确认放弃输入；已提交业务数据保留。
- 切换成功后进入新角色首页，主演示进度来自服务端业务事件。
- 其他标签中的旧角色写操作立即失效；旧标签显示阻断层，要求刷新，不允许继续提交。
- 切换请求已提交但响应结果未送达时，不断言原角色未变；立即阻断旧上下文，并只按服务端当前沙箱角色恢复会话。
- 恢复时若切换结果仍未知，服务端先使原角色上下文版本失效，再返回唯一可继续写入的当前上下文；较晚完成的旧切换不得覆盖恢复结果。
- 当前沙箱或受保护人物已失效时，壳层返回公开角色入口，不在不可用上下文中循环重试。
- 角色与门店不从 URL、请求体或前端下拉框中直接声明为权限来源。

### 5.4 沙箱业务时钟

工具只提供“推进到下一事件”和“+30 分钟”，显示推进前后时间及将受影响的业务类型。时间不能回拨或任意输入，累计最多推进 24 小时。

确认面板说明：

- 会处理跨越的预约/订单超时、爽约、自动完成、考勤缺勤与交接异常。
- 业务时间推进不改变沙箱 24 小时寿命、会话安全、限流或文件清理时间。
- 任一到期处理失败时整次推进失败，不展示半成结果。
- 推进成功后向同一沙箱的其他标签发送失效通知；其他标签从服务端刷新业务时钟与受影响状态，不继续使用旧预览。

### 5.5 沙箱轮换重置

- 重置入口先列出顾客、店员、店长与总部运营四个角色会被替换的数据和故事进度，再进入独立的最终确认；未确认时不能提交。
- 服务端先在单一事务中完整创建并校验最新标准种子沙箱，写入审计、封锁旧沙箱并轮换签名会话；只有全部完成后页面才切换到顾客主演示起点。
- 重置成功后，旧标签立即进入不可绕过的旧沙箱失效阻断，不能继续读取或写入旧对象；刷新后只进入新沙箱。
- 创建或轮换失败时保留当前沙箱和四角色故事，界面不显示伪成功，并使用原幂等键安全重试。
- 新沙箱拥有独立的真实服务器时间 TTL 和从标准种子起点开始的业务时钟；重置不是在原沙箱内逐表清空。
- 同一幂等键重放时，不可变的重置结果保持第一次创建的顾客主演示起点；签名会话上下文单独返回服务端当前角色，避免后续角色切换被重放请求回滚。
- 旧沙箱保留重置操作审计，新沙箱另存来源沙箱事件；两侧都记录业务发生时间与不可推进的服务器记录时间。

### 5.6 主演示清单

清单覆盖：预约、模拟支付、到店、使用、商品订单、报修、备件、验证、看板、导出和重置。每一步包括：

- 当前要切换的角色。
- 目标业务对象与入口。
- 完成条件和已完成证据。
- 下一动作。

清单状态只从主演示顾客及其业务事件、库存流水和导出/重置事件推导，不允许访客手工勾选。

## 7. 合成数据与跨角色主演示

### 7.1 设计稿数据基线

所有页面使用可追溯的合成记录，不使用真实品牌、门店、地址或人物资料。

| 门店工作标签 | 座位与营业时间 | 人员 | 数据特征 |
| --- | --- | --- | --- |
| 旗舰店 | 96 座；24 小时 | 14 名店员、2 名店长 | 晚高峰利用率约 80%–90%，主故事发生地 |
| 标准店 | 64 座；10:00–次日 02:00 | 9 名店员、1 名店长 | 利用率约 55%–70%，包含交接异常 |
| 新店 | 40 座；12:00–24:00 | 6 名店员、1 名店长 | 利用率约 30%–45%，包含缺货、故障和备件领用 |

总部另有 3 名背景运营人员。标准型、竞技型、旗舰型分别表示 1080p/144Hz、2K/180Hz、2K/240Hz 体验；正式硬件品牌与具体 CPU/GPU 不进入设计稿。连锁目录使用 12 种虚构商品和键盘、鼠标、耳机、显示线、网线、电源、散热风扇、内存 8 类备件。

主故事顾客是成长值 860 的白银会员，持有一张预约体验券和一张商品体验券。正式地点名称使用 [`product-ui/README.md`](../README.md) 的共享内容基线：栖光市、棱镜旗舰店、星桥标准店和极点新店。区域名、商品名、备件名和背景人物名继续使用合成内容，不填写可映射真实场所的详细地址。

### 7.2 跨角色主演示

正式原型必须能够按以下顺序完成：

1. `公开入口`：阅读边界，选择顾客，创建新沙箱。
2. `顾客 H5`：在旗舰店选择竞技型座位，创建两小时立即预约，使用预约体验券并完成模拟支付（不扣款）。
3. `店员`：切换角色，在工作台找到该预约，办理到店并在计划开始后进入使用中。
4. `顾客 H5`：从预约详情创建商品订单，使用商品体验券并完成模拟支付（不扣款）。
5. `店员`：把订单推进为制作中、待取或已完成；流程可保留一笔已支付未完成订单以证明设备故障后仍能履约。
6. `共享演示壳`：把沙箱业务时钟推进 30 分钟。
7. `顾客 H5`：提交“耳机右声道无声”报修。
8. `店员`：分派并开始处理，座位进入维护中；使用中预约提前完成，未来完整价格片段产生模拟退款；领用一副替换耳机。
9. `店员`：提交解决说明，报修进入待验证。
10. `店长`：验证成功，报修关闭且座位恢复正常；查看单店看板和相关审计。
11. `总部运营`：查看三店并列变化，导出当前筛选 CSV。
12. `共享演示壳`：确认并重置整个沙箱，返回演示起点。

任何主故事步骤失败都必须保留已提交的合法业务状态，并给出可恢复入口；不能通过前端清单手工跳过。

## 9. 关键页面与交互规格

### 9.0 顾客预约确认 `WEB-C01`

顾客从座位图进入确认状态后，首屏按 `MP-07` 的信息层级展示门店、明确座位、机型档案、完整上海日期时间、时长、半小时价格片段汇总、体验券结果、应付模拟金额和“不扣款”说明。价格明细可以展开到每个半小时片段、规则与整数分金额，不用均价替代价格快照。

预约体验券列表同时展示可用券、不可用券与“不使用体验券”；不可用券必须说明门店、业务、时段、最低金额、有效期或占用状态中的具体原因。选择体验券会即时更新减免与应付模拟金额，减免不得产生负数，金额为零仍使用明确的 `¥0.00`。

确认动作创建一条十分钟排他的待确认预约，不执行模拟支付。成功状态展示保留截止时间、门店/区域/座位、完整预约时段、机型、体验券与不可变应付金额；失败不声明成功。座位或顾客时段冲突会使当前选择失效并提供“返回选座”，体验券冲突则保留座位条件、清除券选择并允许重新确认。相同提交标识与相同内容可以安全重试，内容变化必须要求新的确认。

### 9.0.1 顾客模拟支付与预约详情 `WEB-C02`

待确认预约进入独立的模拟支付旅程，确认、处理中、成功和失败四种状态都必须明确说明“不扣款、不需要真实支付凭证”。支付成功把预约原子转换为已确认，核销已占用体验券，并继续使用创建预约时保存的金额、券和价格片段快照；失败或响应超时时不得猜测结果，使用原提交标识安全重试。

预约详情以服务端当前状态为准，覆盖待确认、已确认、已到店、使用中、已完成、已取消和已过期七种状态。首屏固定展示状态、到店窗口、生命周期进度、门店、座位、机型、完整时段和快照金额；下方可查看体验券/价格快照、模拟支付或退款、关联订单/报修空态及不可变业务事件时间线。待确认状态显示十分钟倒计时，终态不显示非法支付或取消主操作。

顾客可以取消待确认预约或计划开始前的已确认预约。待确认取消不生成退款；已确认取消生成等于快照应付金额的全额模拟退款并恢复体验券，两者都需要明确原因。待确认预约在精确十分钟边界过期，已确认预约在计划开始后十五分钟仍未到店时按爽约过期；详情读取和沙箱业务时钟推进都会惰性、幂等地处理到期结果。每个状态转换、业务事件、副作用、命令结果与审计必须在同一事务中提交；非法转换返回当前状态并写入经过安全过滤的审计记录。

### 9.0.2 顾客柜台商品与商品订单 `WEB-C04`

只有当前顾客在目标门店拥有已到店或使用中的预约时，预约详情才显示“购买柜台商品”。商品目录关联该预约、门店和座位，只展示总部商品中本店已上架的可销售商品、门店售价与服务端可用库存；维修备件、下架商品和其他门店配置不可见。商品数量步进不能超过目录返回的可用数量，分类 Tab、空购物车和低库存提示均可操作，固定提交栏始终与当前购物车件数和小计一致。

确认页保存购物车，不在客户端声明库存成功。商品明细、体验券选择、商品小计、减免和应付模拟金额即时联动；创建动作由服务端在一个事务中整单检查并排他预留整数库存，任一行不足时不创建部分订单、券占用、预留、流水或事件，页面保留原购物车并显示可恢复的“整单库存不足”。每笔待模拟支付订单最多占用一张商品体验券，库存与体验券最多保留十分钟；超时、支付前取消或关联预约在支付前进入终态时全部释放。

订单详情以不可变快照展示商品名称、单价、数量、优惠、总额、关联门店/预约/座位、库存保留倒计时和业务事件。模拟支付操作及结果持续说明“不扣款、不需要真实支付凭证”，相同提交标识可安全重试且不会重复预留；成功进入已模拟支付后，即使关联预约随后终止，商品订单仍作为独立柜台取货对象继续存在。支付前取消恢复库存和商品体验券，终态不显示非法主操作。

### 9.1 店员工作台 `WEB-S01`

工作台按“现在需要处理什么”组织，不按数据库实体平铺。

从上到下的建议层级：

1. 本人班次、模拟签到/签退和交接提醒。
2. 主演示当前动作卡，直接定位主演示对象。
3. 到店窗口内预约、已到店待开始、使用中异常。
4. 已模拟支付待制作、制作中、待取订单。
5. 紧急/较高报修、新建待分派、待验证。
6. 低库存告警摘要。

数量卡必须可以下钻到已应用相同筛选的列表。空状态解释“当前没有待处理事项”，不使用庆祝性文案掩盖数据故障。

### 9.2 预约列表与详情 `WEB-S02` / `WEB-S03`

列表默认当前经营日，支持按状态、时间、区域、机型和异常筛选。每行/卡至少显示：计划时间、座位、顾客工作名、状态、到店窗口、关联异常。

详情固定结构：

1. 当前状态与唯一主要动作。
2. 计划时间、到店窗口、座位、机型与顾客。
3. 模拟金额、体验券与半小时价格快照。
4. 关联商品订单、报修和模拟退款。
5. 不可变业务事件时间线。
6. 有权限角色可见的审计入口。

到店、开始使用、提前结束和取消都使用命令式动作，不提供任意状态下拉框。

### 9.3 商品订单队列与详情 `WEB-S04` / `WEB-S05`

- 队列按履约阶段分组或分段筛选；拖拽不是必需交互，状态推进必须有明确确认和失败结果。
- 详情显示商品名称、单价、数量、优惠、总额快照及关联预约/座位。
- 从已模拟支付依次推进为制作中、待取、已完成，不能跨级。
- 店员在完成前可带原因取消；制作前取消释放库存，制作后取消形成订单损耗。
- 预约因设备故障结束后，已模拟支付订单继续显示在正常履约队列。

### 9.4 报修详情 `WEB-S07`

报修详情是主演示的核心证据页，建议采用以下分区：

- 摘要：优先级、状态、座位、机型、提交来源、处理人。
- 顾客信息：描述、净化图片、公开动态预览。
- 座位与预约影响：正常/维护中、受影响预约及模拟退款。
- 处理：内部说明、解决说明、验证结果。
- 备件：可用数量、已领、已退、实际消耗与关联库存流水。
- 时间线：报修事件与关键审计事件。

开始处理前的确认明确说明座位将进入维护中，并会原子处理当前及未来受影响预约。待验证期间座位仍显示维护中；只有验证成功才同时关闭报修并恢复座位。

分派必须选择本店在职处理人（受保护人物和背景员工使用同一权威员工名单）以及普通、较高或紧急优先级；优先级只用于队列排序与告警，不表达响应时限或 SLA。分派完成前座位保持原运营状态，开始处理只允许当前处理人或同店店长执行。

开始处理以服务端业务时间为边界，在同一事务内提交报修处理中、座位维护中、预约终态、模拟退款、体验券结果、业务事件和审计事件：待确认预约取消且不退款；已确认或已到店但未使用预约取消、全额模拟退款并恢复体验券；使用中预约提前完成，保留当前未完整结束的半小时价格片段，退还未来完整价格片段且不恢复体验券。系统不自动换座，任一写入失败时全部对象保持原状。

维修备件只允许在报修处理中领用。领用必须在同一事务扣减账面库存、创建备件领用记录、库存流水、报修事件与审计事件；库存不足时不得留下任何部分记录。关闭前可从明确领用记录退回未使用数量，累计退回不得超过累计领用。详情持续展示本店可用数量、每次领用、退回、实际消耗、关联流水，以及业务发生时间与入库记录时间。

处理人或同店店长提交 1–500 字解决说明后，报修进入待验证且座位继续维护。验证必须由同店且不同于原处理人的店员或店长执行：失败时记录原因并退回处理中，允许再次领退备件和重新提交解决说明；成功时在同一事务关闭报修并把座位恢复正常。关闭后不提供重新打开或任何维修动作。所有状态动作都使用专用表单，并由服务端返回的当前合法动作决定可见按钮。

内部证据同时展示动作人、业务发生时间与入库记录时间。顾客公开详情只展示公开解决说明、验证失败/成功结果、座位维护或恢复及自己的预约影响，不返回处理人、备件数量、成本、内部笔记或完整审计。

公开说明和内部笔记采用明确不同的输入区域与可见范围标识，避免把内部信息暴露给顾客。

顾客或店员最多添加三张 JPEG、PNG 或 WebP 图片，每张不超过 5 MB。Web 界面应表达单图上传、净化处理中、完成、失败、单图重试和样例图回退；失败时文字报修仍可继续，未经净化的原图不得显示为已保存。重新打开报修时按当前角色与对象范围重新签发短期读取地址；顾客仅查看自己的净化成品图，同店员工和获授权总部按对象范围查看。

店员主动创建报修时必须先选择本店座位，机型由座位带出。若同一座位已有未关闭报修，系统展示已有报修并阻止重复创建；不提供非座位设施入口。

### 9.4.1 本人班次与考勤 `WEB-S09`

本人班次页只读取当前服务端角色对应员工的固定门店范围，不提供员工选择器、跨店切换或总部一线入口。页面按当前上海业务时间展示：

- 当前进行中、已开放签到窗口或签到后仍待本人手动签退的班次，后续计划班次和最近结束班次。
- 班次开始/结束、开始前 30 分钟签到窗口、当前业务时间，以及准时、迟到、缺勤、已签到和已手动签退文字状态；跨午夜结束时明确标注“次日”。
- 不可变原始事实及其业务发生时间、服务器记录时间；签到后仍明确说明签退只能由本人手动触发，系统不自动补写。
- 由服务端当前状态和业务时间推导的唯一下一合法动作；窗口未开启、班次已结束、重复提交和失败安全重试都有明确反馈，不出现任意状态选择器。

模拟签到入口与结果持续说明“不读取定位、人脸或门禁，不接入真实考勤连接器”，且只在当前演示沙箱写入事实。员工只能操作自己的考勤；其他员工、其他门店、顾客与总部请求统一拒绝并追加审计。签到后即使计划结束仍保留本人手动签退入口，系统不得补写签退时间；上一班次未签退时不得为另一班次签到。未来未签到班次可由后续排班管理修改或取消；一旦产生签到、签退或缺勤事实，计划时间与员工/门店归属不可直接修改。

### 9.5 门店商品与库存 `WEB-M06`

列表同时展示：库存类别、账面库存、预留库存、可用库存、独立阈值和告警状态。三项库存数量不能合并成单一“库存”。

操作约束：

### 9.6 价格计划 `WEB-M05`

价格计划表必须显示适用门店、区域、机型、星期、时段、生效区间和版本状态。新价格通过未来生效版本创建，不能直接覆盖历史行。

价格以工作日/周末每半小时整数分记录，同一门店、区域和机型下，钟表范围相交的两个时段不能同时拥有相交的生效区间；首尾相接的时段不视为重叠。跨午夜时段明确标记结束于次日，星期归属按上海时间 `06:00` 经营日边界计算；版本选择以预约开始时的业务时间命中最新有效版本，预约窗口内的每个半小时片段再匹配覆盖该片段的时段计划，不能只用开始片段的单行计划计算整个窗口。预约一旦创建即保存价格片段快照，后续版本创建、归档或生效均不得追溯改写。

创建流程在提交前展示：

- 匹配范围摘要。
- 工作日/周末与半小时价格结果。
- 生效时间。
- 与既有版本的重叠检查。
- 对已有预约价格快照无影响的说明。

### 9.6.1 员工管理 `WEB-M07`

- 店长只管理所属固定门店的背景员工，列表展示员工编号、姓名、岗位、在职状态、未来班次数和未关闭报修分派数；不提供门店选择器或跨店操作。
- 新建员工使用门店内唯一员工编号和姓名，岗位为店员或店长；编辑只修改背景员工姓名和员工编号，停用保留全部历史排班、考勤、交接、报修和审计引用。
- 林澈、周宁、许知远和沈微是共享演示沙箱的四位受保护人物；员工管理只会列出所属门店的周宁与许知远，并禁止编辑、停用或删除，顾客林澈与总部沈微不会进入门店员工写入范围；数据库继续以约束兜底。
- 背景员工存在当前或未来班次、未关闭报修分派时不得停用；阻断状态分别展示依赖数量和可执行去向，不先行隐藏员工或历史记录。
- 总部只读查看三店员工数量、在职状态、未来班次和考勤异常汇总，不继承店长写入动作。

### 9.7 排班与交接 `WEB-M08` / `WEB-M09`

- 排班以半小时网格或等价清晰时间轴表达，允许跨午夜。
- 班次长度 4–12 小时；同一员工不能重叠。
- 覆盖不足是可保存的告警，不表现为阻断错误。
- 已签到班次时间不可直接修改；未来未签到班次可编辑或取消。
- 员工可从班次开始前 30 分钟模拟签到；开始后签到标记迟到，结束时仍未签到标记缺勤。
- 签到后由员工手动签退，系统不自动补写签退时间。
- 考勤更正是追加记录，界面同时保留原始事实和更正结果。
- 交接提交时快照未完成预约、商品订单、报修和库存告警；提交后不可编辑，也不随实时业务变化。
- 补充说明为最多 500 字的规范纯文本，不包含现金盘点、真实支付对账或任意敏感自由字段；提交前持续提示不要填写真实个人信息。
- 只有该班次员工本人可以提交交接；提交后即可手动签退，不必等待接班人确认。另一名已签到的同店员工可以随后确认承接，提交人与确认人、业务发生时间和服务器记录时间均可追溯。
- 班次结束后提交记为迟交；班次结束 30 分钟仍未提交记为逾期未提交；已提交但班次结束 30 分钟仍未确认记为长期未确认。三类交接异常分别展示，并与迟到、缺勤等考勤异常分别解释。
- `WEB-M09` 只读取店长所属门店的交接异常、冻结快照和原始提交/确认事实，不提供交接编辑或审批；店长仅在作为合格同店员工处理本人班次时执行提交/确认。总部只读取链路证据，不替门店提交或确认。

- 总部人员页没有员工、排班、考勤、签到、签退或交接写入口，并持续提示切换到对应门店店长角色处理。人员汇总读取不产生允许访问审计；配置成功写入总部角色审计，非法一线命令和越权门店访问仍追加拒绝审计。

### 9.8 审计与导出 `WEB-M10` / `WEB-H07`

审计列表至少支持时间、演示人物、角色、门店、动作、对象类型和结果筛选。详情显示：

- 演示人物、角色和门店范围。

审计只追加，不提供编辑或删除。店长只看本店，总部看当前沙箱全部三店。

导出使用当前页面的筛选与排序，确认面板显示数据类型、门店范围、经营日范围和预计行数；结果为带 UTF-8 BOM 的 CSV，不使用“导出 Excel”文案。

| 已关闭 | 无状态动作；后续故障新建报修 | 座位正常；不可重新打开 |

### 10.4 库存

`可用库存 = 账面库存 - 预留库存`。三项均为整数且不可为负，预留不可超过账面库存。历史流水不可编辑或删除；销售、损耗、备件领退、入库、盘点和补偿必须显示业务原因与关联对象。

## 11. 经营看板与数据可视化

### 11.1 指标定义

| 指标 | 必须表达的定义 | 禁止的替代表达 |
| --- | --- | --- |
| 模拟营业额 | 已完成预约与已完成商品订单的最终模拟金额 | 实收、利润、GMV |
| 运营座位利用率 | 使用分钟 / 正常可经营座位分钟 | 当前上座率、含维护分母的单一利用率 |
| 维护不可用率 | 维护分钟 / 营业座位分钟 | 故障率、与利用率合并 |
| 订单完成率 | 已完成 / 已进入终态且完成过模拟支付的订单 | 下单或支付转化率 |
| 报修中位处理时长 | 已关闭报修从新建到关闭的中位时长 | 平均响应时长、SLA 达标率 |

### 11.2 看板规则

- 运营座位利用率与维护不可用率必须并列呈现，保持独立分母与定义说明。
- 订单损耗数量和金额独立展示，不混入模拟营业额。
- 未完成商品订单作为当前积压展示，不混入订单完成率分母。
- 考勤分别展示准时、迟到和缺勤；交接只展示异常数量。
- 默认提供当前经营日和最近 7 个经营日，支持在最近 14 个种子经营日内自定义区间。
- 所有按日筛选使用 06:00 经营日边界，跨午夜显示完整日期时间。
- 预约金额按最终未退款的半小时片段归属经营日；商品订单整体归入完成时经营日。
- 总部视图保持三店并列，不生成综合分、最佳门店或默认冠军色。
- 指标卡提供定义或解释入口；图表必须可下钻到构成记录。
- 总部下钻预约、订单、库存或报修时复用相应列表/详情的只读形态，并持续隐藏一线动作。

图表形式可在视觉阶段选择，但必须优先支持准确比较、长中文标签、空数据、异常点和键盘/读屏可访问的文本替代。

## 12. 表格、筛选与配置模式

### 12.1 列表与筛选

- 页面标题区包含对象名、数据范围、经营日范围和获授权主动作。
- 筛选条件应体现在 URL 或可恢复页面状态中，但 URL 不携带可写沙箱凭证或作为权限依据。
- 筛选条区分立即生效条件与需要“应用”的复杂条件；清除筛选有明确入口。
- 列表加载、空结果、真正无数据、权限受限和只读降级使用不同状态。
- 批量操作只在规格明确允许时出现；核心状态机动作以单对象详情为主。

### 12.2 配置保存

- 表单显示作用范围和历史影响，尤其是营业时间、座位、价格、商品和员工停用。
- 被业务引用的配置使用归档/停用，不提供硬删除；仅未被引用草稿可删除。
- 座位编号在门店内唯一；停用座位前展示有效预约和未关闭报修依赖。
- 停用员工前展示当前/未来班次和未完成报修分派依赖。
- 保存成功以后显示服务端确认结果；超时使用原幂等键查询或重试，不先做乐观成功。

## 13. 系统状态与异常恢复

| 场景 | 界面要求 | 可执行恢复 |
| --- | --- | --- |
| 沙箱创建超时/失败 | 不进入部分数据世界；展示创建阶段与安全错误 | 使用同一创建请求重试 |
| 活跃容量已满 | 打开只读标准快照，解释不会保存 | 稍后重试创建 |
| 数据库/API 故障 | 显示只读降级；所有写操作禁用 | 自动/手动重试，不切换可写 Mock |
| SSE 不可用 | 显示“轮询更新”或“需手动刷新” | 轮询、手动刷新 |
| 角色在其他标签被切换 | 阻断旧角色写入，保留未提交表单提示 | 刷新到当前角色 |
| 角色切换响应丢失 | 不断言切换失败或回退旧角色；阻断旧上下文 | 从服务端恢复当前角色与新会话 |
| 沙箱在其他标签被重置 | 旧对象和旧沙箱失效 | 确认丢弃/暂存表单后进入新沙箱 |
| 沙箱自然到期 | 立即停止旧沙箱读取和写入，解释 24 小时边界 | 创建新的标准种子沙箱 |
| 写入超时 | 不显示成功；保持处理中或待确认结果 | 使用原幂等键查询/重试 |
| 幂等键负载冲突 | 显示稳定冲突信息 | 检查当前对象后发起新动作 |
| 预约并发冲突 | 指明座位或顾客时段冲突 | 返回筛选并保留其他条件 |
| 库存并发不足 | 整单失败，无部分订单/流水 | 修改订单或补货后重试 |
| 非法状态跳转 | 当前状态保持不变，显示可执行动作 | 刷新对象状态 |
| 越权/跨店访问 | 安全拒绝，不暴露对象细节 | 返回角色获授权首页 |
| 429 限流 | 显示可重试时间 | 倒计时后重试 |
| 图片上传/净化失败 | 报修文字可继续，原文件不保留 | 重试单图或选择内置样例图 |
| CSV 导出失败 | 不声称已下载；保留筛选 | 使用相同筛选重试 |

错误信息使用稳定中文消息和请求关联 ID；不显示堆栈、SQL、Secret、内部路径、完整请求体或图片内容。

## 14. 组件与模式清单

### 14.1 全局组件

- 公开角色卡、沙箱创建进度和只读降级说明。
- 角色化侧边导航、顶部上下文栏、演示数据标识。
- 角色切换器、主演示清单、沙箱业务时钟、重置确认。
- 数据新鲜度、SSE/轮询状态、手动刷新和旧标签阻断层。

### 14.2 业务组件

- 状态标签、倒计时、业务事件时间线、审计事件详情。
- 经营日选择、日期区间、筛选条、表格、详情抽屉/页面、分页或分段加载。
- 预约到店窗口、价格快照、模拟退款片段。
- 订单履约进度、商品快照、库存预留与订单损耗。
- 报修优先级、处理人选择、公开/内部说明、座位影响、备件领退。
- 账面/预留/可用库存三联数据、低库存告警、不可变流水。
- 排班时间轴、覆盖告警、考勤原始记录与更正、交接快照。
- 指标卡、趋势/比较图、定义说明、下钻链接与导出状态。

### 14.3 命令式操作

以下操作必须使用有业务含义的按钮和确认内容，不能用通用“编辑状态”替代：

- 办理到店、开始使用、提前结束、取消预约。
- 开始制作、标记待取、完成订单、取消订单。
- 分派报修、开始处理、领用/退回备件、提交解决说明、验证成功/失败。
- 手工入库、盘点、补偿流水。
- 模拟签到、手动签退、提交/确认交接、追加考勤更正。
- 切换角色、推进演示时间、导出、重置沙箱。

原因字段在取消、验证失败、库存补偿和考勤更正等场景必填，并显示最大 200 字；报修描述、解决说明和交接说明最多 500 字。

## 15. 内容与术语规范

- 使用“顾客、店员、店长、总部运营”，不使用“玩家、超级管理员、平台管理员”。
- 使用“门店、区域、座位、机型档案”，不把座位称为设备资产或库存位。
- 区分“座位运营状态”与“指定时段的座位可订性”。
- 使用“模拟营业额、模拟支付、模拟退款”，不使用真实收款、实收、利润或退款到账措辞。
- 使用“成长值”，不使用“积分、余额、返现”。
- 使用“商品”“门店商品”“库存项目”“备件”各自正式含义。
- 使用“归档/停用”保留历史引用，不把它写成删除。
- 模拟签到明确写为模拟行为，不出现定位、人脸或门禁授权暗示。
- CSV 导出写为“导出 CSV”，不写“导出 Excel”。
- 时间默认显示上海时间；经营报表明确标注“经营日 06:00–次日 05:59”。

## 16. 响应式与无障碍

### 16.1 断点职责

- 管理系统高保真主稿以 1440px 宽桌面为主要画布，并验证 1280px 与 1024px 横向平板/小屏桌面。
- 1024px 下保持核心业务可执行，可折叠侧边导航并调整次要列；不通过水平裁切隐藏状态、主动作或错误。
- 管理侧不要求在手机窄屏完成全部工作流，但公开入口和顾客 H5 从 360px 起完整可用。
- 复杂表格在 1024px 下优先保留关键列、详情入口和筛选，不以极小字体塞满全部字段。

### 16.2 无障碍要求

- 完整键盘路径、可见焦点、语义标题、表单标签和字段错误关联。
- 状态、优先级、告警、座位和图表不以颜色作为唯一编码。
- 对比度达到基础 RC 的合格要求，禁用状态仍保持可读。
- 对话框正确管理焦点；关闭后返回触发点。
- 图表提供文本摘要和可访问的数据表或明细下钻。
- 顾客 H5 与触控管理面上的关键目标至少 44px。

## 17. 设计交付物与验收

正式管理系统设计稿至少交付：

1. `WEB-G00` 至 `WEB-G07` 的完整共享演示壳，以及所有 `P0` 管理页面。
2. 店员、店长、总部三套导航与权限可见性说明。
3. 可点击的跨角色主演示原型，完整覆盖第 7 节十二个步骤。
4. 预约、订单、报修、库存、排班/交接五条业务操作原型。
5. 正常、空、加载、冲突、超时、越权、旧标签失效、沙箱失效、只读降级、轮询降级和限流状态。
6. 预约、订单、报修的全部状态和合法动作；核心操作不能由任意状态下拉框代替。
7. 单店与总部看板，准确展示双座位指标、订单完成率、库存告警、报修、考勤和交接异常。
8. 1440px 主稿、1024px 管理适配及 360px 公开入口/顾客 H5 关键帧。
9. 组件清单及关键规格：密度、间距、列优先级、焦点、禁用、错误、长文本和对话框行为。
10. 使用真实合成数据和正式中文文案，不使用真实品牌、真实地址、`Lorem ipsum` 或无法由记录推导的图表数字。

验收完成条件：只看设计原型，体验者即可辨认每个角色能做什么、不能做什么，并能从顾客预约一路追踪到店员维修、店长验证、总部比较、CSV 导出和沙箱重置；所有关键结果都有状态、事件或流水证据。
